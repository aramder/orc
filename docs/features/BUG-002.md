**Goal:** every RPDO1 command should produce its TPDO1 confirmation
reliably and promptly, regardless of the state of `canopen_app`'s own
native-USB-CDC serial console.

## Background

Found during real-hardware bench testing (`tools/relay_toggle_test.py`'s
1-10 channel sweep + all-on/all-off, against a real ORC board and a real
Jhoinrch RH-02 USB-CAN adapter, 2026-08). The RPDO1 command path itself
worked correctly from the first run — relays physically confirmed clicking
through in sequence by directly watching/listening to the board. TPDO1
confirmation was unreliable in a specific, repeatable, non-random pattern:

- Roughly every other step's TPDO1 never arrived (2-second host-side
  timeout).
- The steps that did get a TPDO1 consistently reported the *previous*
  step's commanded mask, not the current one — a one-cycle lag, not
  corruption.

Full investigation trail (multiple hypotheses tried and ruled out before
the real cause was found): `.claude/tpdo1-lag-investigation-prompt.md`
(gitignored, local-only handoff doc — not in this repo's tracked history,
summarized here for the permanent record).

**Ruled out, in order:**

1. Host-side stale receive-queue buildup (`tools/relay_toggle_test.py`
   already drains before every send — made zero difference).
2. TWAI hardware auto-retrying an unACKed frame on a bus that hadn't fully
   settled from an earlier error condition (a real, correct mechanism in
   general, and initially looked plausible given a measured TX error
   counter recovering from 127 → 0 over the session) — **directly refuted**
   by re-running the identical sweep only after `tx_error_counter` had held
   at 0 for 10+ seconds with nothing being sent (bus demonstrably settled,
   not just recovering): the sweep still went 0/12, same lag/loss shape.
3. 120Ω termination — confirmed correctly populated on both ends of the
   bus by direct inspection; not the cause.

**Actual root cause**, found by reading the Arduino-ESP32 core's native-USB
Serial implementation (`framework-arduinoespressif32/cores/esp32/HWCDC.cpp`)
directly, not assumed: `handleRpdo1()` logs the incoming RPDO1 via
`Serial.printf()` **before** calling `applyRelayCommand()`, which is where
the TPDO1 send actually happens. `HWCDC::write()`'s documented worst case is
a block of up to `max_consec_timeouts(20) × tx_timeout_ms(100ms) = 2000ms`
when the port reports "connected" (driven by the physical USB link being
up, not by whether any application has the port open for reading) but
nothing is draining the ring buffer. 2000ms is comfortably longer than
`relay_toggle_test.py`'s 2-second confirm window, and lines up almost
exactly with the observed "arrives one cycle late" timing against a 1s
sweep step. This has nothing to do with CAN bus health at all — it
reproduces identically on a demonstrably clean bus, which is exactly what
was observed once the bus-health theory was ruled out.

## Fix

`firmware/src/canopen_app/main.cpp`'s `setup()`:

```cpp
Serial.begin(115200);
Serial.setTxTimeoutMs(20);
```

Bounds any future blocking `Serial` write to ~200ms worst case (2 retries
at the new 20ms timeout) instead of the stock 2000ms — one line, applies
globally to every current and future `Serial` call in the file, not just
the one in `handleRpdo1()`. Confirmed `Serial` really is an `HWCDC`
instance on this build (`platformio.ini` sets both
`ARDUINO_USB_MODE=1`/`ARDUINO_USB_CDC_ON_BOOT=1`, matching `HWCDC.h`'s
guard), and `setTxTimeoutMs()` is a real public method (`HWCDC.h:60`).

**Not done, deliberately left as future work if this ever recurs on a
different call site**: moving the `Serial.printf()` in `handleRpdo1()` to
after the TPDO1 send, or a full audit of every `Serial` call reachable
between a CAN frame's receipt and any time-sensitive response owed to the
bus. `setTxTimeoutMs(20)` alone was sufficient to fully clear the observed
symptom on real hardware (see Acceptance criteria) — the more invasive
fixes weren't needed this pass.

## Depends on

None. Same "found by real-hardware bench testing, root-caused by reading
actual driver source instead of assuming" methodology as BUG-001, different
mechanism (blocking Serial write, not an I2C-probe halt).

## Open questions

- If a similar lag/loss pattern ever reappears on a different `Serial` call
  site (one not bounded by the same global `setTxTimeoutMs(20)` call — e.g.
  if a future change reconfigures the timeout, or a different blocking call
  entirely), the next things to try are the two fixes deliberately not
  applied here: move the specific print, or audit every `Serial` call
  between a CAN frame's receipt and its response. Don't re-derive the
  bus-health theory a third time — it was tested directly and refuted.
