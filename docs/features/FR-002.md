**Goal:** A host (`rigos-core`'s `OrcCanBus`, or anything else on the bus)
should be able to learn "this ORC unit's relay driver (PCA9555) is faulted/
absent" from the CAN wire itself — not only from `canopen_app`'s Serial log,
which nothing on the vehicle is ever listening to in the field.

**Decision, 2026-08-05: yes, do this.**

**Implemented 2026-08-31**, prompted by a real `rigos-core` stress test: an
operator disconnected the ORC's relay-power rail (`B+_TAP` — the same net
feeding both the isolated PCA9555 domain and the relay bus bar) and
commanded an output. The unit kept reporting healthy: its ESP32/CAN side
runs on a separate supply from the isolated relay-power domain, so the
heartbeat never stopped — proving the node alive while the PCA9555 it
depends on was completely dead. `rigos-core`'s BUG-038 (heartbeat-based
liveness check) could not and structurally cannot catch this class of fault;
closing it needed the PCA9555-presence signal firmware already tracks
internally (`g_pca9555Present`, from BUG-001/FR-001) to actually reach the
wire. That gap is exactly what this shard was filed to close.

**Mechanism chosen: TPDO2's byte-7** (was "reserved, send 0"), not EMCY.
Picked for the reasons already weighed below when this was still open — no
new COB-ID, no CiA 301 EMCY payload design, and TPDO2 already broadcasts on
a fixed cadence a host already polls. Because this route was chosen,
**FR-005 (SDO object-dictionary refactor) turned out not to be required** —
that dependency only applied to the object-dictionary/EMCY route.

## Background

Surfaced by [BUG-001](BUG-001.md) (and the sibling [FR-001](FR-001.md) fix
on the USB side): once `canopen_app`'s hard-halt-on-missing-PCA9555 bug was
fixed, the CAN node now correctly stays alive and keeps sending
heartbeat/TPDO2 even without relay hardware — but nothing in what it sends
distinguishes "relay hardware fine" from "relay hardware missing/faulted."
A host watching the bus sees a perfectly normal-looking heartbeat either
way. That's strictly better than the old silent-halt behavior (BUG-001's
whole point), but it's not the same as actually *telling* the host what's
wrong.

Two candidate mechanisms were identified, both already flagged in BUG-001's
Open questions:

1. **TPDO2's reserved byte-7** (chosen — see above).
2. **EMCY** (`kOrcCobIdEmcyBase = 0x080 + NodeID`) — already allocated in
   `orc_canopen.h`, still explicitly "unused this pass." Not used: more
   correct CANopen idiom for a discrete fault *event*, but more work for no
   real benefit here, since byte-7's continuous (not edge-triggered)
   reporting already gives "fault cleared" for free (see below) — one of
   EMCY's main advantages over a polled byte.

## What changed

- `orc_canopen.h`: new `OrcRelayFault` bitmask enum (`ORC_RELAY_FAULT_NONE
  = 0`, `ORC_RELAY_FAULT_HARDWARE_ABSENT = 1u << 0`) — a bitmask, not a
  plain enum, so a future fault condition (real current sensing, if
  `design-inputs.md`'s open item on that is ever resolved) is an additive
  bit rather than a breaking re-encode. `orcPackTpdo2()` gained a
  `relayFault` parameter, written to byte-7.
- `canopen_app/main.cpp`'s `sendTpdo2()`: passes
  `g_pca9555Present ? ORC_RELAY_FAULT_NONE : ORC_RELAY_FAULT_HARDWARE_ABSENT`
  — the existing BUG-001/FR-001 flag, now read outside `canopen_app` for the
  first time.
- `docs/can-protocol-research.md`: TPDO2 table's byte-7 row and a new
  subsection documenting the bitmask, the real motivating case, and why TPDO2
  byte-7 was chosen over EMCY.

**Reported continuously, not edge-triggered**: every TPDO2 send carries
current state, so recovery needs no separate "fault cleared" signal — the
next send after the PCA9555 comes back (FR-001's existing lazy re-probe)
simply reports `0` again. This resolves this shard's own open question about
detected-vs-cleared signaling without adding code for it.

## Cross-repo impact

`rigos-core`'s `OrcCanBus` (`services/io_relay/orc_can.py`, FR-059) does not
decode TPDO2 at all yet — consuming this new byte is a separate FR filed in
that repo (see `rigos-core`'s `docs/features/` for the current ID), which
this shard does not implement. That FR should treat
`ORC_RELAY_FAULT_HARDWARE_ABSENT` as a real fault (`bus_online: false`,
`last_error`) the same way BUG-038 treats a stale heartbeat — a stronger,
complementary signal, not a replacement.

## Acceptance criteria

- [x] TPDO2 byte-7 carries `OrcRelayFault` (bit 0 = PCA9555 absent),
      previously always 0.
- [x] Signal mirrors the existing `g_pca9555Present` flag — no new
      fault-detection logic, only a new way to report a condition already
      tracked.
- [x] Recovery requires no separate signal (continuous reporting).
- [x] `can-protocol-research.md` updated; byte-7 no longer documented as
      reserved.
- [ ] Not yet compiled/flashed against real hardware — no PlatformIO
      toolchain was available in the environment this was written in. Build
      with `pio run -e canopen_app` and flash-test before considering this
      fully verified, not just code-reviewed.
