**Goal:** A host (`rigos-core`'s `OrcCanBus`, or anything else on the bus)
should be able to learn "this ORC unit's relay driver (PCA9555) is faulted/
absent" from the CAN wire itself — not only from `canopen_app`'s Serial log,
which nothing on the vehicle is ever listening to in the field.

**Decision, 2026-08-05: yes, do this.** Logged as a to-do, deliberately not
implemented yet — tackle later, this shard exists so the decision and the
groundwork aren't lost.

## Background

Surfaced by [BUG-001](BUG-001.md) (and the sibling [FR-001](FR-001.md) fix
on the USB side): once `canopen_app`'s hard-halt-on-missing-PCA9555 bug was
fixed, the CAN node now correctly stays alive and keeps sending
heartbeat/TPDO2 even without relay hardware — but nothing in what it sends
distinguishes "relay hardware fine" from "relay hardware missing/faulted."
A host watching the bus sees a perfectly normal-looking heartbeat either
way. That's strictly better than the old silent-halt behavior (BUG-001's
whole point), but it's not the same as actually *telling* the host what's
wrong.

Two candidate mechanisms, both already identified in BUG-001's Open
questions, neither designed in detail yet:

1. **TPDO2's reserved byte-7.** `orc_canopen.h`'s `orcPackTpdo2()` already
   writes byte-7 as `0` ("reserved"). Cheapest option — no new COB-ID, no
   new message type, TPDO2 already broadcasts on a fixed cadence so a
   host already polling it for bus-health would pick this up for free.
   Downside: repurposes a byte the wire-format doc currently documents as
   reserved — needs a `can-protocol-research.md` update, and isn't really
   what "reserved" is conventionally for in CANopen (reserved bytes are
   usually left for the *protocol* to extend, not repurposed ad hoc by one
   implementation).
2. **EMCY** (`kOrcCobIdEmcyBase = 0x080 + NodeID`) — already allocated in
   `orc_canopen.h`, explicitly flagged there as "unused this pass (stretch
   goal per prompt)." The CANopen-idiomatic way to report exactly this kind
   of fault: a real emergency object with an error code/register, sent once
   on fault detection (and arguably once on recovery, if the PCA9555 comes
   back — lazy re-probe is already implemented per FR-001's fix). More
   correct, more work: needs a real (even if minimal) CiA 301 EMCY payload
   format decision, not just a spare byte.

Neither is implemented. This shard exists to hold the decision ("yes,
signal it") and the tradeoff research already done, so whoever picks this
up next doesn't have to re-derive it from BUG-001's Open questions section.

## Cross-repo impact, not yet scoped

`rigos-core`'s `OrcCanBus` (`services/io_relay/orc_can.py`, FR-059) does
not currently decode TPDO2 or EMCY at all — it only speaks RPDO1/TPDO1/
heartbeat. Whichever mechanism gets picked here, consuming it on the
rigos-core side is a separate, later FR in that repo, not folded into this
one. Filing this now only to make sure the dependency is visible; not
starting it.

## Scope (not finalized — pick one at implementation time)

1. Decide TPDO2-byte vs EMCY (see Background) — this is the FR's first
   real task when picked up, not decided here.
2. If TPDO2 byte: update `orc_canopen.h`'s `orcPackTpdo2()`, document the
   new byte-7 meaning in `can-protocol-research.md`'s TPDO2 section
   (currently says "reserved").
3. If EMCY: design a minimal CiA 301 emergency-object payload (error
   code, error register, at minimum), implement `twaiSend()` of it from
   `canopen_app` on fault detection (and optionally recovery), document in
   `can-protocol-research.md`.
4. Either way: `canopen_app`'s `setup()`/`handleRpdo1()` (the
   `g_pca9555Present` flag from BUG-001) is the natural place to trigger
   the new signal — no new fault-detection logic needed, just a new way to
   report a condition already being tracked.

## Open questions

- TPDO2-byte vs EMCY — the actual decision this FR exists to make, not yet
  made.
- Should the signal be "fault detected" only, or also "fault cleared" on
  recovery? FR-001's lazy re-probe pattern (`requireRelayHardware()`) means
  `canopen_app` could plausibly do the same, but that's not designed here
  either.
