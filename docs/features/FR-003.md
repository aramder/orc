**Goal:** Let a host learn an ORC unit's **currently applied channel bitmask
without commanding anything first.** Today the only way to find out what the
relays are doing is to tell them what to do — which, for a latching contactor,
destroys the answer in the act of asking.

## Why this is HIGH, and why it is not an ORC-internal nicety

`rigos-core` **FR-062** (channel state observation and reconciliation) exists
because the auxiliary power system is moving to **latching contactors**, whose
failure mode is *stuck-connected*: they hold state with nothing running, so a
daemon restart has no idea what the hardware is doing, and one of the guesses
parallels a starter battery with a LiFePO4 bank across a 110 A path.

FR-062's whole premise is *observe before you command*. **ORC cannot currently
support that.** This shard is the firmware half.

## Current behaviour — verified in the tree 2026-08-07

TPDO1 (`0x180 + NodeID`) carries the applied channel bitmask and is correct as
far as it goes. `rigos-core` already consumes it (`orc_can.py:127`, `:265-268`).
The problem is purely **when** it is sent.

| Fact | Evidence |
|---|---|
| `sendTpdo1()` has exactly one call site: `applyRelayCommand()` | `main.cpp:142-157`, `:164` |
| `applyRelayCommand()` is reached only from `handleRpdo1()` and the RPDO1-timeout fail-safe | `main.cpp:212`, `:281` |
| `loop()` has periodic timers for TPDO2, heartbeat, and the health check — **none for TPDO1** | `main.cpp:393-416` |
| Object `1800h` (TPDO1 comm parameter) is **not implemented at all** | repo-wide search for `1800` returns nothing |
| Object `1801h` sub-index 5 (TPDO2 event timer) **is** implemented, 1000 ms default, SDO-writable, NVS-persisted | `orc_canopen.h:149-150`, `main.cpp:62`, `:312-315` |
| The SDO server recognises **one** (index, sub-index) pair — 1801h/5 — and aborts everything else `0x06020000` | `orc_canopen.h:181-202` |
| CiA-401 `6000h`/`6200h` are named in the protocol doc as the conceptual mapping but are **not** SDO-readable objects | `docs/can-protocol-research.md:216`, `:230` |
| Object `1017h` (producer heartbeat time) is not an OD object; the 1000 ms interval is a hard-coded constant | `main.cpp:63`, `:412-415` |

**Consequence for the host:** `_last_applied_mask` is empty until the daemon
commands something. A freshly-started daemon has nothing to read, and the only
way to populate it is to transmit an RPDO1 — which for a latching contactor is a
command to change state. **The measurement destroys the thing being measured.**

## Preferred approach — SDO read, not periodic TPDO1

> **DECIDED 2026-08-07 (recommendation; revisit if bench work contradicts it).**

Add an **SDO-readable object returning the applied channel bitmask**. The host
performs an expedited upload at startup, gets the answer, and commands nothing.

Why this over making TPDO1 periodic:

- **Query semantics match the need.** FR-062 wants an answer at one specific
  moment (daemon start). A broadcast is the wrong shape for a question asked
  once.
- **No steady bus or I2C load.** `sendTpdo1()` calls `pca9555ReadInputPorts()`
  (`main.cpp:152`). A periodic TPDO1 puts a PCA9555 read on the I2C bus every
  interval, forever, on every node.
- **No log spam.** With the PCA9555 absent — which is the current bench state,
  see below — the read-back-failure warning at `main.cpp:152` fires **once per
  period** instead of once per command.
- **It composes with the existing SDO path.** An expedited-upload branch already
  exists (`ccs == 2`, `orc_canopen.h:220-229`); it just returns the TPDO2
  interval today.

**Object choice:** prefer the CiA-401 generic-I/O read object the protocol doc
already names (`6000h`, read digital inputs / applied outputs) over inventing a
manufacturer-specific index, so a generic CANopen tool can read it too. Confirm
the sub-index convention against CiA-401 before implementing — **do not guess
the mapping.**

**Do the periodic option as well only if bench work shows the SDO round-trip is
unreliable.** If so, the parameter is object `1800h` sub-index 5 (TPDO1 event
timer), directly analogous to the working `1801h`/5, and the `loop()` timer
pattern is already proven three times over — copy the TPDO2 block. Default it to
**off (0)**, not to a period: a host that wants periodic state asks for it.

## Implementation note — the object dictionary is hand-rolled

`orcHandleSdoRequest()` is a straight-line if-chain against a single hard-coded
`kOrcSdoObjectIndex` / `kOrcSdoObjectSubIndex` pair (`orc_canopen.h:168-241`).
There is no table and no loop over entries.

Adding a second object means either a second index branch or **refactoring to a
small table first.** Prefer the table — this shard adds the second object and
FR-002 is likely to add a third, so the if-chain is already at the point where
it stops being the simple choice.

Estimated size: roughly 30–60 lines plus the doc updates, either way.

## Scope

1. Refactor the SDO object handling to a small table of entries (index,
   sub-index, size, read/write, accessor) rather than a hard-coded pair.
2. Add a **read-only** entry returning the applied channel bitmask, using the
   CiA-401 object confirmed against the standard.
3. Return the **applied** mask — the value last written to the relay hardware
   and read back where possible — not the commanded mask. If read-back is
   unavailable (PCA9555 absent/faulted), the SDO read must **abort**, not return
   the commanded value. A host that cannot distinguish "this is what the
   hardware is doing" from "this is what I last asked for" is back where it
   started.
4. Update `docs/can-protocol-research.md` and `firmware/README.md`: the message
   table, the object dictionary listing, and an explicit statement that TPDO1
   remains event-driven.
5. Coordinate with `rigos-core` **FR-062** — that shard consumes this.

## Acceptance

- [ ] An SDO expedited upload of the new object returns the applied channel
      bitmask, with **no RPDO1 sent and no channel state changed** — asserted by
      observing the bus during the exchange.
- [ ] With the PCA9555 absent or faulted, the read **aborts** with a defined
      abort code rather than returning the commanded mask.
- [ ] The existing 1801h/5 read and write still work unchanged after the table
      refactor (regression).
- [ ] An unknown (index, sub-index) still aborts `0x06020000`.
- [ ] TPDO1's event-driven behaviour is unchanged.
- [ ] `rigos-core`'s `OrcCanBus` can populate `_last_applied_mask` at startup
      without transmitting a command — verified against this firmware, not a
      mock.
- [ ] Docs updated; the object dictionary listing matches the implementation.
