> # ⚠️ SPLIT 2026-08-29 — the USB half of this FR is DONE
>
> This FR originally covered **both** transports. The USB half shipped
> incidentally as part of **FR-004**'s consolidation and is **not** outstanding
> work. What remains is **CAN only**, and the title narrowed accordingly — from
> *"…readable on demand, not only after a command"* to *"…readable on demand
> **over CAN**"*.
>
> The shared prerequisite — replacing the hard-coded SDO handler with a real
> object-dictionary table — is now **FR-005**, because **FR-002 needs it too**.

**Goal:** Let a CAN host learn an ORC unit's **currently applied channel bitmask
without commanding anything first.** On CAN today the only way to find out what
the relays are doing is to tell them what to do — which, for a latching
contactor, destroys the answer in the act of asking.

## Status by transport — verified in the tree 2026-08-29

| Transport | Can a host read applied state without commanding? | Evidence |
|---|---|---|
| **USB** | **YES — done (FR-004).** `GET <ch>` returns `STATE <ch> ON/OFF`; `STATUS` returns a 10-char mask | `main.cpp:654-684` |
| **CAN** | **NO — this FR.** The SDO server recognises exactly one object; TPDO1 is event-driven | `orc_canopen.h:151-152`, `:183`, `:194` |

### Why the USB half already satisfies the original ask

`GET` and `STATUS` both call `readAppliedMaskFromHardware()`
(`main.cpp:220-225`), which is `pca9555ReadInputPorts()` plus
`orcPca9555ToRelayMask()` — a **real hardware read**, not a shadow, and not the
commanded value.

Critically it also satisfies the *applied-vs-commanded* requirement the original
Scope §3 called out: on read failure it returns **`ERR I2C_READ_FAILED`** rather
than falling back to what was last commanded. A host that cannot distinguish
"this is what the hardware is doing" from "this is what I last asked for" is back
where it started, and the USB path does not make that mistake.

`rigos-core` already consumes it — `orc_usb.py:209-216` parses `STATUS`, and
`:222` describes itself as *"Prove the transport is reachable (PING) and read
back applied state."*

### What is still missing on CAN

| Wanted | State | Evidence |
|---|---|---|
| SDO-readable applied-mask object (CiA-401 `6000h`/`6200h`) | **Not implemented.** The SDO server recognises exactly `1801h`/`5` and aborts everything else `0x06020000` | `orc_canopen.h:151-152`, `:183`, `:194` |
| Object `1800h` sub5 (TPDO1 event timer), the periodic fallback | **Not implemented** — the index does not appear in the repo | repo-wide search |
| Object-dictionary table refactor | **Not done** — still a hard-coded single index pair | `orc_canopen.h:151-152` |

> **⚠️ Do not mistake `211a10a` for this work.** *"Add startup status poll +
> stale-frame drain"* is **host-side tooling**, and the SDO read it added is of
> **`1801h`/`5` — TPDO2's event timer**. Its own commit message says it is
> *"harmless, doesn't touch relay state."* It exists because a board at node ID 0
> stays silent until something is sent to it. Useful, unrelated.

### TPDO1 did improve, but not in a way that helps startup

TPDO1 now fires on **any** real applied-state change — including USB-originated
ones, not just CAN commands — and carries a genuine hardware read-back rather
than the commanded value (`main.cpp:376`, `:394-404`). That is strictly better.

It is still **event-driven**, sent only from `applyRelayCommand()`. A freshly
started host has nothing to read, which is exactly the case this FR exists for.

## Why this is HIGH

`rigos-core` **FR-062** (channel state observation and reconciliation) exists
because the auxiliary power system uses **latching** contactors, whose failure
mode is *stuck-connected*: they hold state with nothing running, so a daemon
restart cannot know what the hardware is doing, and one of the guesses parallels
a starter battery with a LiFePO4 bank across a 110 A path.

FR-062's premise is *observe before you command*. **The CAN transport cannot
support that today.** This shard is the firmware half.

Note the scope of the block: FR-062's **I2C** path is unblocked (load-side
voltage sensing), and its **USB** path is served by FR-004's `STATUS`. It is
specifically the **CAN** transport that is waiting on this.

## Preferred approach — SDO read, not periodic TPDO1

> **DECIDED 2026-08-07, unchanged. Revisit only if bench work contradicts it.**

Add an **SDO-readable object returning the applied channel bitmask**. The host
performs an expedited upload at startup, gets the answer, and commands nothing.

Why this over making TPDO1 periodic:

- **Query semantics match the need.** FR-062 wants an answer at one specific
  moment (daemon start). A broadcast is the wrong shape for a question asked once.
- **No steady bus or I2C load.** The TPDO1 path performs a
  `pca9555ReadInputPorts()`; a periodic TPDO1 puts an I2C read on every node
  every interval, forever.
- **It composes with the existing SDO path.** An expedited-upload branch already
  exists (`orc_canopen.h:220-229`); today it only returns the TPDO2 interval.
- **Bus headroom is now a measured constraint, not a theoretical one.** BUG-003's
  real-hardware work traced sub-second commanding failures to genuine
  `CAN_ERR_CRTL` bus-level error frames and settled on a documented **~1 s safe
  commanding interval**. An unsolicited periodic broadcast per node eats exactly
  that headroom. A one-shot query does not.

**Object choice:** prefer the CiA-401 generic-I/O read object the protocol doc
already names (`6000h`) over a manufacturer-specific index, so a generic CANopen
tool can read it too. **Confirm the sub-index convention against CiA-401 before
implementing — do not guess the mapping.**

Periodic TPDO1 (object `1800h` sub5, directly analogous to the working
`1801h`/5) remains the documented fallback **only** if the SDO round-trip proves
unreliable on the bench. Default it to **off (0)**, not to a period.

## Scope

1. **Land FR-005 first** — the object-dictionary table. Do not add a second
   hard-coded index branch.
2. Add a **read-only** entry returning the applied channel bitmask, using the
   CiA-401 object confirmed against the standard.
3. Return the **applied** mask, read back from hardware exactly as the USB path
   already does via `readAppliedMaskFromHardware()`. If read-back is unavailable
   (PCA9555 absent or faulted), the SDO read must **abort** with a defined abort
   code — **never** return the commanded value.
4. Update `docs/can-protocol-research.md` and `firmware/README.md`: the message
   table, the object dictionary listing, and an explicit statement that TPDO1
   remains event-driven.
5. Coordinate with `rigos-core` **FR-062**, which consumes this.

## Acceptance

- [ ] An SDO expedited upload of the new object returns the applied channel
      bitmask, with **no RPDO1 sent and no channel state changed** — asserted by
      observing the bus during the exchange.
- [ ] With the PCA9555 absent or faulted, the read **aborts** with a defined
      abort code rather than returning the commanded mask.
- [ ] The existing `1801h`/5 read and write still work unchanged after FR-005's
      refactor (regression).
- [ ] An unknown (index, sub-index) still aborts `0x06020000`.
- [ ] TPDO1's event-driven behaviour is unchanged.
- [ ] `rigos-core`'s `OrcCanBus` can populate its applied-mask cache at startup
      without transmitting a command — **verified against this firmware on real
      hardware, not a mock.** The board is now in hand, so there is no reason to
      accept a simulated result.
- [ ] Docs updated; the object dictionary listing matches the implementation.
