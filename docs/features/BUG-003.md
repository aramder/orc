**Goal:** `canopen_app` should keep sending Heartbeat/TPDO2 on schedule and
confirm RPDO1 commands via TPDO1 promptly, regardless of how quickly RPDO1
commands arrive, within any commanding rate a real host is likely to use.

## Background

Found via randomized RPDO1 testing, 2026-08-10 (ad-hoc scripts, not
committed — `tools/_adhoc_random_test.py`, `tools/_adhoc_trace_test.py`),
done specifically to stress-test BUG-002's fix beyond the fixed 1s/2s
cadence that fix was verified against. **BUG-002's fix is confirmed
correct for its own symptom** — this is a second, distinct issue uncovered
by testing at a faster cadence than the original investigation used.

**Cadence characterization** (20 random masks/run, real ORC board, Jhoinrch
RH-02 adapter, node ID 0):

| Inter-command spacing | Result | Failure signature |
|---|---|---|
| 2.0s | 20/20 | none |
| 1.0s | 17/20 | clean drops only (no TPDO1 at all — no lag/mismatch) |
| 0.5s | 1/20 | mostly lag (previous-round's mask) + drops |
| 0.3s | 1/20 | same lag+drop mix |

The 1.0s→0.5s transition is a cliff, not a gradual decline — inconsistent
with simple bus/queue congestion scaling smoothly with rate.

**Full-trace run, 0.5s cadence, no mid-run `drain_stale_frames()` calls**
(a fixed methodology bug in the first trace attempt — draining right before
every send discards any Heartbeat/TPDO2 that arrived during the previous
round's sleep, silently hiding the periodic traffic; the corrected trace
never drains mid-run and logs every frame continuously) — see raw output in
`.claude/tpdo1-lag-investigation-prompt.md` if a follow-up session adds it
there, summarized here:

- Rounds 1-4: clean. TPDO1 arrived correctly each time, ~0.8-1.6s after
  send (already looser than BUG-002's fixed-cadence result, but correct).
  Heartbeat and TPDO2 both observed once each, early (t=0.002s, t=0.003s).
- Round 5: TPDO1 did not arrive within its 2s window.
- From round 5 onward, for the rest of the ~30s run: **no further
  Heartbeat or TPDO2 frames were observed on the bus at all.** Every
  subsequent TPDO1 arrived carrying the *previous* round's mask, at a
  roughly steady ~2.4s cadence — slower than the 0.5s the host was actually
  commanding at, and never catching up.

**Interpretation, not yet confirmed against firmware source for this
specific mechanism**: this doesn't look like a per-frame CAN-level loss
(BUG-002's mechanism, already fixed and independently reconfirmed clean at
slower cadence). The disappearance of Heartbeat/TPDO2 — firmware's own
independent 1Hz-class periodic timers, not conditional on RPDO1 traffic at
all in the code as read for BUG-001/BUG-002 — points at `loop()` itself
getting stuck somewhere for extended, cumulative periods once RPDO1 commands
arrive faster than it can fully process each one (I2C round-trip in
`applyRelayCommand()`/`reassertPca9555State()`, or repeated blocking
`twai_transmit()` calls backing up), rather than dropping/delaying isolated
frames. Once stuck, it appears to fall into a steady slower rhythm and does
not recover within the run — worth checking on a longer run whether it ever
catches back up on its own once RPDO1 traffic stops.

## Root cause and fix — 2026-08-10, code-level, not yet re-verified live

Did the "Not yet done" direct code read of `applyRelayCommand()`/
`reassertPca9555State()`/`twaiSend()` this pass, plus checked the actual
TWAI driver API (`driver/twai.h`) for what it exposes about queue state —
found a real, well-supported mechanism, not just characterized the
symptom further:

**`TWAI_GENERAL_CONFIG_DEFAULT`'s `tx_queue_len` is 5** (confirmed in the
driver header, same fact BUG-002's investigation already established).
Every status message this firmware sends — TPDO1, TPDO2, Heartbeat, SDO
response — reports *current* state. A copy still sitting unsent in that
5-deep queue isn't just "delayed," it's actively wrong the moment a
fresher one becomes due, because it will report stale data whenever it
finally transmits. Nothing in `twaiSend()` (unchanged since before
BUG-002, still a single `twai_transmit()` attempt with no retry on
failure) previously stopped one stale message from sitting in the queue
and blocking everything queued behind it in strict FIFO order, once the
send rate outpaced however fast the bus could actually drain the queue for
any reason — this explains both halves of the observed symptom at once:
the "always the previous round's mask" TPDO1s (draining old backlog, not
sending fresh data) and the total Heartbeat/TPDO2 silence (their own
periodic sends hitting the same jammed queue and failing outright, silently,
with no retry).

**Fix, in `twaiSend()`** (`firmware/src/canopen_app/main.cpp`): before
enqueueing any message, check `twai_get_status_info()`'s `msgs_to_tx` field
(confirmed present in `twai_status_info_t`) — if nonzero, something older
is still backlogged and hasn't left the transceiver yet. Call the driver's
own `twai_clear_transmit_queue()` (confirmed present, public API) to
discard it before enqueueing the fresh message, so the newest status
always wins the queue instead of stacking up behind stale ones. Only acts
when a backlog is actually detected — a no-op under normal healthy
conditions where the queue should already be empty between sends.

**Known, accepted tradeoff, documented in the code**: this can
occasionally discard a message queued moments earlier in the *same*
`loop()` pass by a different `twaiSend()` call (e.g. TPDO2 and Heartbeat
both firing in one iteration) if it genuinely hasn't left the wire yet —
rare at 125 kbit/s, and a single missed periodic broadcast self-corrects
on the next 1-second cycle regardless. Far preferable to the total,
non-recovering starvation this fixes.

**Not done**: instrumented firmware-side timing to independently confirm
this is *the* mechanism (vs. e.g. genuine bus contention/error-passive
suspend-transmission delays throttling the actual drain rate, which this
fix would improve the *symptom* of — freshest-status-wins instead of
stale-forever — without necessarily raising the underlying sustainable
throughput). Build-verified and flashed to the real board on COM6 this
pass (`orc-canopen-fr004`, confirmed alive via `PING`/`STATUS` immediately
after); **the actual CAN-side stress re-test (the randomized-mask sweep at
0.5s/0.3s cadence that originally found this) has not been re-run against
this fix** — I don't have working driver access to the Jhoinrch RH-02
adapter in this environment (see the investigation doc's BUG-002 handoff
section for why) and deliberately didn't try to fix that myself mid-bug.

## Round 2, same day — TX-queue theory insufficient; found and fixed a bigger contributor; found a genuine hardware/bus-level factor too

Re-tested with working live CAN access (`python-can`/`gs_usb`, previously blocked by a missing `libusb` DLL on `PATH` — see `tools/README.md`'s "gs_usb on Windows" section, fixed this pass). The `twai_clear_transmit_queue()` fix above, tested alone, **did not resolve the symptom**: 1/15 confirmed, same shape (stale TPDO1s, missing Heartbeat/TPDO2).

**Found the bigger contributor by direct A/B real-hardware testing**: ran the identical 0.5s-cadence sweep twice, back to back, changing exactly one thing — whether a second script was concurrently reading `canopen_app`'s own USB-serial console (COM6) while the CAN test ran. Nothing reading it: 1/15. Something reading it: **15/15**, TPDO1 arriving within single-digit milliseconds of every single RPDO1. Same firmware binary, same cadence, same bus.

Root cause: `BUG-002`'s `Serial.setTxTimeoutMs(20)` fix was itself under-specified — `HWCDC.cpp`'s `max_consec_timeouts` is a **hardcoded constant (20)**, not something that call adjusts, so the real worst-case block per `Serial` write call is `20 x 20ms = 400ms`, not the "~200ms (2 retries)" originally claimed in this codebase's comments (corrected in both places it was wrong). `handleRpdo1()`/`applyRelayCommand()` issue several `Serial` calls per RPDO1 (the RPDO1 log line, up to 10 `STATE` lines, the BUG-003 backlog notice) — each one individually bounded, but **compounding** to multiple seconds when nothing drains the console, explaining the "never recovers" shape directly.

**Fix**: added `printBestEffort()` — checks `Serial.availableForWrite()` and skips the print entirely rather than blocking. Applied to the specific hot-path calls implicated (the `handleRpdo1()` log line, moved to *after* the TPDO1 send as well; the `STATE`-line loop; the TX-backlog notice). Re-tested CAN-only (no console reader, the failing scenario): **1/15 → 6/15** — first 6 rounds now clean where before only round 1 ever succeeded. Real, substantial improvement, not a full fix.

**New finding on the remaining ~60% failure rate, not yet firmware-explainable**: inspected raw frame attributes on the bus during a fresh run (`tools/_adhoc_inspect_frame.py`, ad hoc) and found a real `is_error_frame=True` CAN error frame recurring roughly every **~2.4s**, arbitration ID `0x004` with data byte `0x0c` — decoded per the Linux SocketCAN error-frame convention: `CAN_ERR_CRTL` (`0x004`, "controller problems") with `CAN_ERR_CRTL_RX_WARNING | CAN_ERR_CRTL_TX_WARNING` (`0x04 | 0x08 = 0x0c`) — both error counters crossing the warning threshold. Each occurrence lands immediately before the next TPDO1 finally gets out. **This did not appear in BUG-002's original 1Hz-cadence investigation** (which confirmed a clean, TEC=0 bus under that slower traffic pattern) — it appears specific to this faster, tightly-interleaved bidirectional RPDO1-in/TPDO1-out cadence, and is evidence of a genuine bus/controller-level condition, not purely a firmware logic issue. Not yet determined whether this is the adapter's own controller, ORC's TWAI controller, or a real signal-integrity issue that only manifests under back-to-back bidirectional traffic at this rate.

## Round 2, continued — Heartbeat/TPDO2 still fully starved; error frames confirmed independent of the Serial fix

Watched a full 20-second run at 0.5s cadence for TPDO2 specifically (`tools/_adhoc_tpdo2_watch.py`, ad hoc) — **zero TPDO2 or Heartbeat frames arrived, the entire run**, unchanged from before `printBestEffort()`. The `0x004`/`CAN_ERR_CRTL` error frames continued on the same ~2.0-2.4s cadence, completely unaffected by the Serial fix (same timing, same warning-bit pattern, one run even showed the data byte return to `0x00` between events — consistent with the error counters oscillating across the warning threshold repeatedly, not sitting in one fixed state).

**Conclusion**: `printBestEffort()` is a real, valid fix for a real, separate problem (confirmed by the clean same-session A/B: 1/15 → 15/15 with a console reader attached) — but it does not touch this second, independent mechanism. The periodic health-check block (`checkTwaiRecovery()` + `reassertPca9555State()` + TPDO2 send + Heartbeat send, all in one 1-second `loop()` pass) is still never completing successfully during sub-second RPDO1 commanding, and the recurring `CAN_ERR_CRTL` warning-threshold error frames — present with or without the Serial fix — point at a genuine CAN-bus-level condition (real signal integrity, contention, or adapter-controller behavior specific to fast bidirectional traffic), not firmware logic. This is not something further `Serial`/software tuning is likely to resolve — it needs either real electrical-level investigation (oscilloscope/protocol analyzer on the physical bus during this exact traffic pattern) or acceptance as a real rate ceiling.

**Recommendation**: `printBestEffort()` stays — genuine improvement, no downside. For the remainder: given `~1s` cadence is independently confirmed clean (BUG-002's own 12/12 re-verification) and every finding past that point implicates real bus-level error-warning conditions rather than a fixable firmware bug, recommend closing this out as **BUG-003 resolved to the extent firmware can address it, with a documented safe commanding interval (~1s) rather than continued blind firmware iteration** — per this bug's own originally-stated acceptance option, and consistent with what a production/rigOS-core commanding pattern is very unlikely to exceed in practice (see this shard's own "Not yet done" list, original pass).
