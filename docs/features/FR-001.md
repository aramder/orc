## SUPERSEDED 2026-08-10 by FR-004 — usb_bench retired, consolidated into canopen_app

User's explicit ask, after real-hardware bring-up on the actual ORC PCB
today: "there should be USB control built into the main application
firmware - I want to be able to drive from either CAN or USB interfaces."
The standalone `usb_bench` sketch this FR built is retired; its protocol,
findings, and fixes below are folded into `canopen_app` — see
[FR-004.md](FR-004.md) for the consolidation work. This shard is kept, not
deleted, because the real-hardware bug hunt below (the PCA9555-gate reopen)
is genuine project history and the exact bug shape recurred and got fixed
the same way in `canopen_app` as `BUG-001` — useful precedent, not dead
weight.

**Goal (historical):** Give ORC a USB-serial bench/debug interface — same
native USB-C port already wired for flashing, CDC-ACM, plain-ASCII line
protocol — so relay-channel logic can be driven and observed from a
terminal or a script before any CAN transceiver hardware is wired up,
without touching the resolved CAN-exclusive production control path.

## REOPENED 2026-08-05 — the implementation defeats its own stated purpose

**Fix applied and real-hardware re-verified, 2026-08-05, same day.** Same
Pi + same bare ESP32-C3 devkit (no PCA9555) that found the bug, re-flashed
with the fix and driven live over its USB-CDC port:

```
HB 7678 / HB 8678 / HB 9678          <- heartbeat flowing before any command sent
PING    -> PONG orc-usb-bench-fr001   <- live response, not just a boot-log line
VERSION -> VERSION orc-usb-bench-fr001 Aug  5 2026 20:25:22
STATUS  -> ERR NO_RELAY_HARDWARE      <- clean, specific error, not a hang
SET 3 ON -> ERR NO_RELAY_HARDWARE
GET 3    -> ERR NO_RELAY_HARDWARE
BOGUS    -> ERR UNKNOWN_CMD           <- framing/error handling still fine
```

Heartbeat kept interleaving between every command response, confirming
`loop()` runs continuously and no command handler blocks it. Every "New"
acceptance item from the reopen is now confirmed on real hardware, not just
build-verified. Back to `implemented`.

First real-hardware test (Raspberry Pi building/flashing `usb_bench` onto a
bare ESP32-C3 devkit over USB, no ORC PCB, no PCA9555) found that
**`usb_bench` cannot be reached at all without a PCA9555 already ACKing on
the I2C bus** — not `SET`/`GET`/`STATUS` (expected to need it), but
`PING`/`VERSION` too, which shouldn't.

Root cause, `main.cpp`'s `setup()`:

```cpp
Wire.beginTransmission(kPca9555Addr);
uint8_t probe = Wire.endTransmission();
if (probe != 0) {
  Serial.printf("ERR PCA9555 did not ACK at 0x%02X (endTransmission=%u). Halting -- relay "
                "control is this sketch's entire purpose. Run i2c_scanner first.\n",
                kPca9555Addr, probe);
  while (true) delay(1000);
}
```

`loop()` — and therefore `pollSerial()`/`handleLine()`, i.e. the entire
command interface — is never reached if the PCA9555 doesn't ACK. Confirmed
on real hardware, 2026-08-05: boots, prints its banner (including a
`PONG orc-usb-bench-fr001` line from the *boot log*, not a live response to
a `PING` command — the loop never starts), then hangs in
`while (true) delay(1000)` forever. `endTransmission=2` (NACK on address).
Independently corroborated with `i2c_scanner`: bus idles clean (SDA/SCL
both HIGH), genuinely nothing attached — not a wiring fault, just no
PCA9555 present, exactly the situation a bare bring-up devkit is always
going to be in until wired to a real ORC board.

**Why this is the whole point, not a nitpick**: this FR's own Background
section states the motivating use case is testing "before any CAN
transceiver hardware is wired up" — i.e. *before full ORC hardware exists*.
A bare ESP32-C3 devkit with nothing else attached is exactly that scenario,
and it's currently useless for it. The interface can't even confirm it's
alive (`PING`) without the one piece of hardware it was supposed to let you
defer.

**Fix direction** (not locked, implementer's call on exact shape):
- `setup()`'s I2C probe should set a flag (e.g. `g_pca9555Present`) instead
  of halting.
- `loop()` must always run regardless of that flag — `PING`, `VERSION`,
  and basic protocol handling (`ERR BAD_ARGS`/`ERR UNKNOWN_CMD`/framing)
  should work with zero I2C hardware present.
- `SET`/`GET`/`STATUS` are the commands that legitimately need the
  PCA9555 — when `g_pca9555Present` is false, they should return a clear,
  specific error (e.g. `ERR NO_RELAY_HARDWARE`) rather than attempting I2C
  transactions that will just fail the same way every time.
- Decide (and document, don't silently pick): does the firmware re-probe
  for the PCA9555 periodically/lazily in case it gets hot-plugged onto the
  bus later during a bench session, or is a fresh boot required to pick up
  newly-present hardware? Either is defensible for a bench tool; just
  record the choice.
- The heartbeat (`HB <uptime_ms>`) should also work with no PCA9555
  present — it doesn't touch relay hardware at all, no reason it should be
  gated by this.

## Background

Full protocol spec, rationale, and explicit scope boundary already written
up in [`docs/usb-bench-interface-spec.md`](../usb-bench-interface-spec.md) —
this shard tracks implementation against that spec, doesn't restate it.
Key points carried over:

- Bench/dev tool only. `docs/design-inputs.md`'s "Primary control path"
  resolution (CAN, exclusively, no wireless) is about the ESP32-C3's radio
  losing to CAN for application control — it says nothing about the
  already-present native USB-C, wired only for programming/flashing. This
  reuses that same port for a serial bench interface; no BOM change, no
  board respin, no contradiction of the CAN-exclusive decision.
- Motivating use case: rigOS's `io_relay` daemon (`rigos-core`, FR-059)
  already validated the CAN backend end-to-end against real hardware, but
  bringing up ORC's *own* firmware needs CAN transceiver hardware wired
  correctly before anything on the ORC side can be exercised — this gives a
  transceiver-free path to drive/observe relay logic over the same cable
  used to flash it.
- Point-to-point by construction (one USB cable = one ORC unit) — no NodeID
  concept, unlike the CAN protocol.

## Scope

1. **New sketch `firmware/src/usb_bench/main.cpp`** — its own PlatformIO
   environment (`usb_bench`), individually flashable like every other
   sketch in this directory.
2. **Transport**: native USB CDC-ACM (`Serial`, already routed off UART0
   onto native USB by the existing `ARDUINO_USB_MODE`/
   `ARDUINO_USB_CDC_ON_BOOT` build flags — no new flags needed). 115200
   documented as the nominal baud in the README even though USB CDC ignores
   it, per the spec's own note (`pyserial` etc. still require a value be
   passed).
3. **Framing**: ASCII, one command/response per line, `\n`-terminated,
   `\r` tolerated/stripped. 128-byte max line length, `ERR LINE_TOO_LONG` +
   discard-until-`\n` on overflow. Case-insensitive command words.
4. **Commands**: `PING`, `VERSION`, `SET <ch 1-10> ON|OFF`, `GET <ch>`,
   `STATUS` — exactly the table in the spec. Relay I/O reuses
   `firmware/lib/orc_relay_map/` (the real, schematic-confirmed
   channel-mask <-> PCA9555-register mapping, same lib `pca9555_bringup`
   and `canopen_app` already share) — **not** a third hand-rolled copy of
   that mapping.
5. **Unsolicited lines**: `HB <uptime_ms>` every 1000ms; `STATE <ch>
   ON|OFF>` once, immediately, on every actual applied-state change
   (command-driven or fail-safe-driven).
6. **Errors**: `ERR BAD_CHANNEL` / `ERR BAD_ARGS` / `ERR UNKNOWN_CMD` /
   `ERR LINE_TOO_LONG`, per spec.
7. **Fail-safe decision (spec explicitly left open, decided here)**: idle
   timeout de-energizes all channels, for philosophical consistency with
   CAN's own RPDO1-timeout fail-safe (`can-protocol-research.md`'s
   recommendation, already implemented in `canopen_app`) — a bench tool
   that behaves differently from the real control path on "commander went
   away" seemed like the wrong default. Timeout set to **30000ms**, much
   longer than CAN's 5000ms: this is an interactive human-typed interface
   (a person pausing to think, or reading `STATUS` output, shouldn't trip
   a safety timeout the way a genuinely vanished CAN host should). Any
   received line — valid or malformed — counts as activity and resets the
   timer, since a malformed command is still evidence a host is present
   and typing. Recorded here and in `firmware/README.md`, not silently
   picked.
8. **Docs**: `firmware/README.md` gets a `usb_bench` section matching the
   existing per-sketch write-ups (`canopen_app`'s section is the closest
   template — real functionality, not just a bring-up walk pattern).
9. **New, from the reopen**: `setup()` must not halt the whole sketch on a
   missing PCA9555. See "REOPENED" section above for the exact fix shape.

## Acceptance criteria

- [x] `usb_bench` builds clean as its own PlatformIO environment
      (`pio run -e usb_bench`).
- [x] **Fixed 2026-08-05**: All 5 commands implemented exactly per the
      spec's response table. `setup()` no longer halts on a missing
      PCA9555 — a `g_pca9555Present` flag replaces the old
      `while (true) delay(1000)` gate, and `loop()` always runs. Build-
      verified only so far (`pio run -e usb_bench` SUCCESS) — **not yet
      re-flashed to the real hardware that found this bug**, see the item
      below.
- [x] Channel <-> PCA9555 mapping goes through `lib/orc_relay_map/` only —
      no second hand-rolled copy of the routing-driven table.
- [x] Idle-timeout fail-safe implemented and its parameters documented in
      both this shard and `firmware/README.md`.
- [x] `firmware/README.md` updated with a `usb_bench` section (and its
      "What this is not" section corrected to stop claiming `usb_bench` had
      zero real-hardware contact — it found this bug on real hardware).
- [x] **Fixed**: `PING`, `VERSION`, and basic framing/error handling
      (`ERR BAD_ARGS`/`ERR UNKNOWN_CMD`/`ERR LINE_TOO_LONG`) no longer sit
      behind the PCA9555 gate — code-reviewed and build-verified, **not yet
      re-run on the bare devkit that originally found this**, and confirmed:
      see the real-hardware re-verification item below for the transcript.
- [x] **Fixed**: `SET`/`GET`/`STATUS` now call a shared `requireRelayHardware()`
      helper that makes one lazy re-probe attempt and returns
      `ERR NO_RELAY_HARDWARE` (a distinct, documented code, not a reused
      generic I2C-failure message) if the PCA9555 still isn't present. A
      write/read failure on a previously-present PCA9555 also drops the
      flag, so a mid-session disconnect re-probes on the next relay command
      instead of repeating the same failing transaction forever.
- [x] **Decided (was an open fix-direction question)**: re-probe policy is
      **lazy, on-demand** — attempted automatically inside
      `requireRelayHardware()` whenever `SET`/`GET`/`STATUS` is called and
      the PCA9555 wasn't already known-present; no periodic background
      poll. A fresh boot is not required to pick up hardware that gets
      hot-plugged onto the bus mid-session. Recorded here and in
      `firmware/README.md`'s `usb_bench` section.
- [x] **Real-hardware re-verification of this fix — confirmed 2026-08-05.**
      Same Pi, same bare ESP32-C3 devkit, no PCA9555, that found the
      original bug: re-flashed with the fix, driven live over USB-CDC.
      `HB` flowed before any command was sent; `PING` -> `PONG
      orc-usb-bench-fr001` and `VERSION` both answered live (not boot-log
      lines); `STATUS`/`SET 3 ON`/`GET 3` each cleanly returned `ERR
      NO_RELAY_HARDWARE`, no hang; `BOGUS` still correctly `ERR
      UNKNOWN_CMD`; heartbeat kept interleaving between every response,
      confirming `loop()` never blocks. Full relay-I/O validation (does
      `SET`/`GET`/`STATUS` actually drive/read a real PCA9555 correctly)
      remains separately blocked on a PCA9555/real ORC board, neither in
      hand yet - unchanged from before this reopen, and not what this FR
      was reopened over.

## Open questions

- **rigos-core-side `orc_usb.py` backend** — explicitly out of scope per
  the spec (a human with a serial terminal is a complete consumer on its
  own). Natural follow-up FR in the `rigos-core` repo if/when wanted; not
  filed here.
- **Multi-unit bench setups** — spec is deliberately point-to-point, no
  NodeID. If a bench ever needs to talk to 2+ ORC units over USB
  simultaneously, that's host-side serial-port bookkeeping (which
  `/dev/ttyACM*` is which unit), not a firmware protocol change.
- **Does `canopen_app` have the same pattern?** Not checked as part of this
  reopen — `canopen_app` legitimately needs the PCA9555 for its entire job
  same as `usb_bench` claims to, but if it has an equivalent
  halt-the-whole-sketch gate, CAN-side liveness (heartbeat, at minimum)
  might have the identical problem. Worth a quick look, not filed as its
  own item yet.
