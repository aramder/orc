**Goal:** `canopen_app` should join the CAN bus (heartbeat, TPDO2 health,
SDO) regardless of whether the PCA9555 relay-driver chip is present —
relay I/O (RPDO1/TPDO1) is the one thing that legitimately needs it, not
CAN presence itself.

## Background

Same bug shape as [FR-001](FR-001.md)'s reopen (`usb_bench`), found while
looking for it deliberately after that fix landed, per that shard's own
"Open questions" note flagging `canopen_app` as unchecked. Confirmed
present: `main.cpp`'s `setup()` used to do

```cpp
Wire.beginTransmission(kPca9555Addr);
uint8_t probe = Wire.endTransmission();
if (probe != 0) {
  Serial.printf("PCA9555 did not ACK...\n");
  while (true) delay(1000);
}
```

**before** `twai_driver_install()`/`twai_start()` ever ran. Worse than the
`usb_bench` case: this is the real production control path, not a bench
tool. A PCA9555 fault took the entire CAN node dark — no heartbeat, no
TPDO2 health/error-counter report, nothing — indistinguishable on the bus
from "unit not powered" or "no CAN connectivity at all." From `rigos-core`'s
side (`OrcCanBus`, FR-059), a node with a working CAN transceiver and MCU
but a bad I2C connection to its own relay driver would look identical to a
node that's completely absent — exactly the silent-failure mode `io_relay`'s
own BUG-016 was fixed to avoid on the rigOS side.

## Fix

`firmware/src/canopen_app/main.cpp`:

1. New `g_pca9555Present` flag, set (not gated on) by the boot-time I2C
   probe. `setup()` no longer halts on `probe != 0` — logs a `WARNING` and
   continues; the "configure PCA9555 as outputs" register writes only run
   in the `else` (present) branch.
2. TWAI driver install/start, NMT boot-up heartbeat, and the rest of
   `setup()` run unconditionally either way.
3. `handleRpdo1()` checks `g_pca9555Present` before attempting any I2C
   write. If absent: logs, still resets the RPDO1 fail-safe timer (a valid
   command was received, even if it couldn't be applied — the host isn't
   "gone"), and returns without calling `applyRelayCommand()`/`sendTpdo1()`
   — avoids repeating an I2C transaction that would fail identically on
   every single RPDO1.
4. `loop()` itself needed no changes — `sendHeartbeat()`/`sendTpdo2()`/
   `checkTwaiRecovery()` never touched I2C in the first place, they were
   only unreachable because `setup()` never returned.

Not changed, deliberately out of scope for this bug: no new wire-protocol
signaling of "relay hardware absent" (e.g. a TPDO2 reserved-byte flag, or
using the already-allocated-but-unused EMCY COB-ID `0x080+NodeID`). Right
now a host only learns about this via `canopen_app`'s Serial log, not
anything on the CAN bus itself — heartbeat/TPDO2 keep flowing normally,
they just don't distinguish "relay hardware fine" from "relay hardware
missing." Real gap, flagged in Open questions, not fixed here — it's a
wire-protocol change with cross-repo consequences (rigos-core's `OrcCanBus`
doesn't decode TPDO2 or EMCY at all today), deserves its own decision, not
a rider on this bug fix.

## Acceptance criteria

- [x] `canopen_app` builds clean (`pio run -e canopen_app`).
- [x] `setup()` no longer halts when the PCA9555 doesn't ACK — verified via
      live serial capture on the exact bare ESP32-C3 devkit (no PCA9555)
      that has neither an ORC PCB nor a CAN transceiver wired: boot
      completes, TWAI driver reports started, no hang.
- [x] `handleRpdo1()` degrades instead of attempting a doomed I2C write
      every command when hardware is absent.
- [x] **Confirmed 2026-08-05, real hardware, same devkit**: `loop()` now
      actually calls `sendHeartbeat()`/`sendTpdo2()` with no PCA9555 present
      — live boot log shows `TWAI started: TX=GPIO21 RX=GPIO20, 125 kbit/s,
      Node ID 4` then `Initialization complete. Entering Operational.`,
      followed by real transmit attempts on COB-ID `0x704` (heartbeat, node
      4) and `0x284` (TPDO2, node 4). Before this fix, none of `loop()` was
      ever reached at all with no PCA9555 present.
- [ ] Real-CAN-bus validation (frames actually observed landing on a real
      bus with no PCA9555 attached) — **still not done**, this specific
      bench ESP32-C3 has no CAN transceiver wired at all (separate hardware
      gap
      from the PCA9555 one), so TWAI frames can't be observed going out
      over real differential CAN from this exact setup. Serial-log
      confirmation only for the TWAI-side behavior.

## Open questions

- **Should a hardware fault (missing/failed PCA9555) be signaled on the CAN
  bus itself**, not just Serial? Candidates: repurpose TPDO2's currently-
  reserved byte-7 as a relay-hardware-health flag, or finally implement the
  already-allocated-but-unused EMCY message (`kOrcCobIdEmcyBase`,
  `docs/can-protocol-research.md`'s own "stretch goal"). Either is a real
  wire-protocol addition — needs its own decision, and if EMCY, would need
  `rigos-core`'s `OrcCanBus` updated to decode it (currently doesn't decode
  TPDO2 or EMCY at all). Not filed as its own FR yet.
