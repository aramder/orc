> # ▶ NEXT FIRMWARE ITEM — build this before FR-003
>
> **Severity here (MEDIUM) is lower than the FR it unblocks (FR-003, HIGH).
> That inversion is real and intentional — do not let a severity-sorted queue
> reorder them.** FR-003 cannot be built first: it needs a second SDO object,
> and the handler is a hard-coded single (index, sub-index) pair, so adding one
> without this refactor means a parallel branch that this FR then has to unpick.
>
> MEDIUM reflects that this ships no wire-visible behaviour on its own, not that
> it can wait.

**Goal:** Turn `orcHandleSdoRequest()` from a straight-line `if`-chain over one
hard-coded object into a small **table of object-dictionary entries**, so adding
an object is a table row rather than another branch.

**Split out of FR-003 on 2026-08-29** because it is a shared prerequisite:
**FR-003** (SDO-readable applied channel mask) and **FR-002** (relay-hardware
fault signalling) both add object-dictionary surface. Doing the refactor once,
on its own, keeps each of those a small readable diff instead of two competing
rewrites of the same function.

## Current state — verified 2026-08-29

The SDO server recognises exactly **one** (index, sub-index) pair and aborts
everything else with `0x06020000`:

```c
static const uint16_t kOrcSdoObjectIndex    = 0x1801;   // orc_canopen.h:151
static const uint8_t  kOrcSdoObjectSubIndex = 0x05;     // orc_canopen.h:152

if (reqIndex    != kOrcSdoObjectIndex)    { /* abort */ }   // :183
if (reqSubIndex != kOrcSdoObjectSubIndex) { /* abort */ }   // :194
```

That single object is TPDO2's event timer — 1000 ms default, SDO-writable,
NVS-persisted. It works; the shape does not scale.

The download (write) and expedited-upload (read) paths at `orc_canopen.h:220-229`
are both wired to that one object, so a second object cannot be added without
either a parallel branch or this refactor.

## Scope

1. **A table of entries**, each carrying at minimum: index, sub-index, data size,
   access (read-only / read-write / write-only), and accessors. The existing
   `1801h`/5 entry becomes the first row and its behaviour must not change.
2. **Keep the abort behaviour exact.** An unknown index or sub-index must still
   abort `0x06020000`. Aborts are part of the wire contract and a generic CANopen
   tool will exercise them.
3. **Distinguish "unknown index" from "unknown sub-index of a known index"** if
   CiA 301 requires different abort codes for the two — **check the standard, do
   not assume they are the same.** The current code aborts both identically,
   which is a simplification that a table makes easy to fix properly.
4. **Read accessors may fail.** FR-003 needs an object whose read depends on
   live I2C hardware and must **abort** rather than return a stale or commanded
   value. The table's accessor signature must be able to express failure — a
   plain `uint32_t` return cannot, and designing that out now avoids reworking
   the table one FR later.
5. Keep it **small**. This is a firmware object dictionary for a 10-channel
   relay box, not a general CANopen stack. A handful of rows and a loop is the
   target; do not grow a framework.
6. Update the object-dictionary listing in `docs/can-protocol-research.md` so it
   describes the table rather than the single hard-coded pair.

## Acceptance

- [x] `1801h`/5 read and write behave **exactly** as before — same value, same
      NVS persistence, same defaults. This is a pure refactor of the dispatch;
      any behaviour change here is a defect. Wire encoding re-derived from
      first principles per size (`n = 4 - sizeBytes`) and checked to reproduce
      the old fixed `0x4B` byte-0 exactly at `sizeBytes=2` — see
      `orc_canopen.h`'s comment at the encoding site.
- [x] An unknown index still aborts `0x06020000`.
- [x] An unknown sub-index of a **known** index aborts with whatever CiA 301
      specifies, and the shard records which code and why. **Finding:** the
      pre-refactor code already used two different constants here
      (`kOrcSdoAbortObjectDoesNotExist` for index misses,
      `kOrcSdoAbortSubIndexDoesNotExist` = `0x06090011` for sub-index misses
      on a known index) — this shard's "today both abort identically" premise
      was stale by the time of writing; verified against the tree
      (`orc_canopen.h:183-204` as of `d79b50c`) and against CiA 301's
      abort-code table as reproduced in open CANopen primers (Kvaser, Lely).
      The table refactor preserves this split unchanged, plus adds
      `0x06010002` (write to read-only) / `0x06010001` (read from write-only)
      for the access-mismatch cases the old single-object code couldn't hit.
- [x] A read accessor can signal failure, and that failure becomes an SDO abort
      rather than a fabricated value (`0x06060000`, "access failed due to a
      hardware error"). Demonstrated with a deliberately failing test entry
      (`runSdoHwFailureSelfTest()` in `main.cpp`, run once at boot against a
      local throwaway table, not `kSdoObjectTable` — no new wire-visible
      object), since FR-003's real case does not exist yet.
- [x] Adding a new object is a table row plus its accessors — no new branch in
      the request handler.
- [ ] **Verified on real hardware, not only a build. The board is in hand —
      but it is physically connected to the Raspberry Pi over USB right now,
      actively driven by a parallel rigos-core session validating FR-069.
      Per that session's hardware-lock handoff, this branch was NOT flashed
      or bench-tested.** `pio run -e canopen_app` succeeds (RAM 4.7%, Flash
      26.6%) and that is the only verification performed. This box must stay
      unchecked until someone flashes the board and exercises: (1) a normal
      `1801h`/5 read and write over CAN, confirming identical behaviour and
      NVS persistence to before; (2) an SDO request to an unknown index and
      to an unknown sub-index of `1801h`, confirming the two abort codes
      differ as coded; (3) the boot-time self-test log line reads PASS. CI
      green plus synthetic fixtures is known-insufficient for this project —
      do not treat the clean compile above as satisfying this item.

## Notes

- **Pure refactor, no new wire behaviour.** It ships no feature on its own, which
  is the point: it is reviewable in isolation and de-risks FR-002 and FR-003.
- **Blocks FR-003**, and should land before **FR-002** for the same reason.
- Respect the **~1 s safe commanding interval** (BUG-003) in any bench test.
- The `1801h`/5 object is also what `tools/`'s startup poll reads to wake a
  silent node-ID-0 board (commit `211a10a`) — so a regression here breaks the
  bench tooling, not just the protocol.
