**Goal:** `canopen_app` (the real application firmware) should accept relay
commands from either interface -- CAN (RPDO1, as today) or USB
(`usb_bench`'s plain-ASCII protocol) -- against the same physical relay
state, instead of USB control only existing in a separate sketch. One
firmware, two control paths, one PCA9555, one source of truth for applied
state.

## Background

Real-hardware bring-up today (2026-08-05) exercised both `canopen_app` and
`usb_bench` independently on the same real ORC PCB. User's explicit ask:
"there should be USB control built into the main application firmware - I
want to be able to drive from either CAN or USB interfaces." Two decisions
made before implementation, per `docs/hardware-workflow.md`'s "surface the
trade-off, don't pick silently" convention:

- **Retire the standalone `usb_bench` sketch** (user's explicit choice) --
  `canopen_app` becomes the one real firmware going forward, not two
  binaries duplicating relay-I/O logic against the same PCA9555.
- **Fail-safe interaction: "any activity resets both timers"** (user's
  explicit choice, over "keep fully independent"). Implemented as a
  context-sensitive unified timeout, not a naive shared-clock merge -- see
  Scope item 3 for why a naive merge doesn't actually achieve the intent
  (the tighter of two shared-clock thresholds always dominates and makes
  the looser one dead code; the actual fix needed is threshold selection
  based on *which* interface supplied the most recent activity, not just a
  shared timestamp).

## Scope

1. **Port the USB command interface into `canopen_app`**: `PING`, `VERSION`,
   `SET <ch> ON|OFF`, `GET <ch>`, `STATUS`, unsolicited `HB <uptime_ms>`
   (1000ms) and `STATE <ch> ON|OFF` (on real applied-state change, from
   *either* interface) -- same wire protocol `docs/usb-bench-interface-spec.md`
   already specifies, same line framing (128-byte cap, `\n`-terminated, `\r`
   tolerated, case-insensitive commands).
2. **One relay-state authority, not two.** `applyRelayCommand()` becomes the
   single choke point both `handleRpdo1()` (CAN) and the new `SET` handler
   (USB) call through. It re-asserts PCA9555 direction (existing
   `reassertPca9555State()`, unchanged), reads back applied state once, and
   from that single read-back: broadcasts TPDO1 on CAN AND emits any
   changed-channel `STATE` lines on USB -- **every real applied-state
   change is now visible on both interfaces regardless of which one caused
   it**, not just the interface that issued the command. This is a genuine
   behavior upgrade from the two-separate-sketches world, not just a code
   merge.
3. **Unified fail-safe, context-sensitive, not a naive shared clock.** A
   naive "one shared last-activity timestamp, both checks read it" does NOT
   implement "any activity resets both" correctly: since CAN's threshold
   (5000ms) is shorter than USB's (30000ms), a shared clock means the 5s
   check always fires first, making the 30s USB grace period unreachable
   dead code -- exactly the nuisance ("USB session gets killed every 5s
   with no CAN master present") the decision was meant to avoid. Real fix:
   track which interface supplied the most recent activity
   (`ActivitySource::CAN` vs `::USB`) alongside the shared timestamp, and
   pick the applicable threshold based on that source -- 5000ms after CAN
   activity, 30000ms after USB activity. A pure-CAN session keeps the
   original strict RPDO1 fail-safe; a pure-USB session gets the original
   generous human-typing grace; either interface's activity postpones the
   other's countdown, matching the decision's intent without dead code.
4. **PCA9555 presence handling ported wholesale, not narrowed.**
   `usb_bench`'s `probeAndConfigurePca9555()` + lazy on-demand re-probe
   (attempted from `SET`/`GET`/`STATUS` whenever hardware isn't currently
   known-present) replaces `canopen_app`'s boot-only probe. `handleRpdo1()`
   gets the same lazy re-probe treatment it didn't have before (BUG-001
   only stopped it from halting the whole sketch; it never re-probed after
   boot) -- a PCA9555 hot-plugged mid-session is now picked up by either
   interface, not just detected-once-at-boot.
5. **Documented compromise, not silently accepted**: `canopen_app`'s Serial
   output was always a human debug log (prose diagnostics -- RPDO1 dumps,
   TWAI errors, SDO writes, etc.), not the strictly line-clean protocol
   `usb_bench` alone was. Once the same UART/USB-CDC port serves as the
   real bench-protocol channel, that debug prose is now interleaved with
   `PONG`/`STATE`/`ERR`/`HB` lines. Not cleaned up in this pass (would be a
   much larger refactor of every `Serial.print*` call in the file) --
   documented explicitly in `docs/usb-bench-interface-spec.md` instead: a
   host-side parser against this firmware MUST tolerate/ignore unrecognized
   lines, matching the spec's own existing "check first token" robustness
   requirement for interleaved unsolicited lines, just now covering
   diagnostic prose too, not only other protocol lines.
6. **Retire `usb_bench`**: delete `firmware/src/usb_bench/`, remove
   `[env:usb_bench]` from `platformio.ini`, update `firmware/README.md`
   (remove/retire its section, redirect to `canopen_app`'s now-unified
   one), mark `docs/features/FR-001.md` as superseded by this FR (not
   silently deleted -- the shard and its real-hardware findings stay as
   history), update `docs/features/LOG.md`.

## Acceptance criteria

- [ ] `canopen_app` builds clean with the merged interface.
- [ ] `SET`/`GET`/`STATUS`/`PING`/`VERSION` work over USB exactly per
      `docs/usb-bench-interface-spec.md`'s response table, reusing (not
      duplicating) the PCA9555 I/O and relay-mask helpers already in this
      file/`lib/orc_relay_map/`.
- [ ] A relay change commanded via CAN (RPDO1) produces a `STATE` line on
      USB; a relay change commanded via USB (`SET`) produces a TPDO1 frame
      on CAN. Single read-back feeds both, not two separate I2C reads.
- [ ] Fail-safe: a pure-CAN session still de-energizes ~5s after RPDO1
      silence; a pure-USB session gets ~30s grace between commands; either
      interface's activity postpones the other's countdown.
- [ ] `SET`/`GET`/`STATUS` attempt a lazy re-probe (not `ERR
      NO_RELAY_HARDWARE` immediately) if the PCA9555 wasn't previously
      known-present; `handleRpdo1()` gets the same treatment.
- [ ] `usb_bench` sketch removed; `platformio.ini` has no `[env:usb_bench]`;
      `firmware/README.md` updated; `FR-001.md` marked superseded (not
      deleted); `LOG.md` updated.
- [ ] Real-hardware validation on the actual ORC PCB in hand right now --
      SET-over-USB and confirm CAN TPDO1 observed (once a transceiver is
      wired up, per the user's own concurrent hardware work today), and/or
      RPDO1-over-CAN confirmed to produce a USB `STATE` line.

## Open questions

- **Serial-output protocol cleanliness** (see Scope item 5) -- flagged as a
  documented compromise, not resolved. A future pass could gate/prefix
  diagnostic prose (e.g. always `# ` or similar) to make it mechanically
  filterable, if a real host-side driver (`rigos-core`'s hypothetical
  `orc_usb.py`) needs stricter parsing than "ignore unrecognized lines."
- **DTR/RTS-triggered reset while USB bench protocol is in active use** --
  found and explained today (native USB-CDC auto-reset, not an ORC
  feature): a host application that closes/reopens the serial port
  carelessly can trigger a full chip reset, de-energizing everything. Not
  new to this FR, but now more consequential since USB is a first-class
  control path in the main firmware, not just a bench sketch. Worth a
  README/spec callout for future host-driver authors; not a firmware fix
  (the reset mechanism is Arduino-ESP32-core/esptool infrastructure, not
  something `canopen_app` can or should override).
