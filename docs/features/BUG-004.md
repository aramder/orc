**Goal:** `printBestEffort()` must be all-or-nothing on a line-oriented
protocol stream. Either the whole line goes out, or nothing does — never
part of a line with its trailing `\n` dropped.

## Found by

rigos-core session, real hardware, 2026-08-29, board idle with CAN
disconnected (`can0` DOWN on the Pi). **Board not flashed to investigate —
it was in active use elsewhere when this was found.** Filed as a shard first,
fixed once the board freed up (same session, later the same day — see
Acceptance).

## Symptom

30 `STATUS` rounds captured over the USB CDC stream, 64 lines total:

| | |
|---|---|
| HB lines parseable as `HB` | 0 / 34 |
| HB lines glued to noise | 34 / 34 |
| `STATUS` replies clean | 30 / 30 (command responses NOT affected) |

Observed glued line:
```
...so this status stays curTWAI TX backlog...stays curHB 65515
```
Truncated mid-word, at the same point ("...stays cur") every time — not
random corruption, a consistent cutoff.

## Root cause — CORRECTED after real-hardware investigation (2026-08-29)

The originally suspected cause, kept below for the record, was **wrong** —
fixing it alone did not clear the symptom on real hardware, which is what
led to finding the real one.

**Originally suspected** (`firmware/src/canopen_app/main.cpp:296-300`):

```cpp
static void printBestEffort(const char *s) {
  if (Serial.availableForWrite() > 0) {
    Serial.print(s);
  }
}
```

The guard checks `availableForWrite() > 0` — at least 1 byte of room — but
hands the entire string to `Serial.print()`. The theory: combined with
BUG-002's `Serial.setTxTimeoutMs(20)`, a write that doesn't fit would time
out partway through and drop the remainder. **This was fixed first
(comparing against `strlen(s)` instead of `> 0`, see Fix) and reflashed —
the glued lines were still 100% present, byte-for-byte identical, proving
this was not the mechanism.**

**Actual root cause**, found by computing the exact formatted-string length
of the `twaiSend()` backlog notice (`main.cpp:354-374` after the SDO-table
refactor lines shift; the message itself is unchanged):

```cpp
char msg[128];
snprintf(msg, sizeof(msg),
         "TWAI TX backlog detected (%lu msg(s) still queued) before sending COB-ID "
         "0x%03lX -- clearing stale backlog so this status stays current (BUG-003).\n",
         (unsigned long)status.msgs_to_tx, (unsigned long)cobId);
```

At its shortest realistic substitution (`msgs_to_tx=2`, `cobId=0x280`) this
formats to **143 characters + NUL = 144 bytes** — but `msg` is only 128
bytes. `snprintf()` itself silently truncates to 127 chars + NUL *before
`printBestEffort()` is ever called* — the string handed in already lacks
its tail, newline included. Truncating at exactly char 127 of this format
lands at `"...stays cur"` — reproduces the observed cutoff point exactly,
independently confirmed with a standalone length calculation before
touching hardware again.

`printBestEffort()`'s `> 0` guard was a real bug (see Fix — hardened
regardless, it's still capable of causing this class of corruption for any
future call site with a correctly-sized-but-still-too-large-for-the-buffer
string), but it was not *this* bug's mechanism. The undersized `char
msg[128]` was.

## Consumer impact

`rigos-core`'s `orc_usb.py::_handle_unsolicited` does `parts[0] == "HB"`.
A glued line starts with `TWAI`, not `HB`, so every heartbeat line is
silently dropped whenever this fires. Degrades rather than fails outright
(liveness falls back to `PING`), but the passive heartbeat path is 100%
non-functional under exactly the condition — CAN backed up — where
diagnostics matter most. Will reproduce in-vehicle whenever the CAN side
backs up, not just on this idle/CAN-disconnected bench condition.

## Fix

Two changes, both real, only the second actually cleared the symptom:

**1. `printBestEffort()` hardened (defense-in-depth, not this bug's cause):**
compare `Serial.availableForWrite()` against `strlen(s)` and skip the
entire message if it won't fit, rather than committing to a partial write:

```cpp
static void printBestEffort(const char *s) {
  size_t len = strlen(s);
  if (Serial.availableForWrite() >= (int)len) {
    Serial.print(s);
  }
  // else: drop the whole line. A partial line (missing its \n) is worse
  // than no line at all on this line-oriented protocol -- it corrupts
  // whatever comes after it too, not just itself.
}
```
`<string.h>` added to the includes (not previously present; `ctype.h`
happened not to pull in enough on this toolchain to make `strlen` visible
without it).

**2. The actual fix: enlarge the undersized buffer** at the `twaiSend()`
backlog-notice call site from `char msg[128]` to `char msg[192]` — sized
generously past the ~144-byte actual max rather than trimmed to the exact
byte count, so a future wording tweak to this message doesn't silently
reopen the same class of bug.

**Not changed**: the other two `printBestEffort()` call sites
(`applyRelayCommand()`'s `STATE` lines, `handleRpdo1()`'s RPDO1 log line) —
checked by hand against their own worst-case formatted length and both fit
comfortably inside their existing buffers (`STATE 10 OFF\n` = 13 chars in a
24-byte buffer; the RPDO1 line's worst case is ~61 chars in an 80-byte
buffer). Heartbeat and `STATUS` don't go through `printBestEffort()` at all
(see Open questions).

## Related history

- **BUG-002**: introduced the blocking-write hazard this bug's partial
  writes trace back to (`setTxTimeoutMs(20)` bounds *how long* a write
  blocks, not whether it completes).
- **BUG-003**: introduced `printBestEffort()` itself, to avoid blocking
  entirely on a hot path — this bug is the gap that fix left: not-blocking
  was solved, not-corrupting wasn't.

## Open questions

- Heartbeat (`sendHeartbeat()`) and `STATUS` use plain `Serial.print`/
  `printf` calls, not `printBestEffort()` — worth confirming (separately)
  whether those sites have their own partial-write exposure, or whether
  they're short enough / infrequent enough that `setTxTimeoutMs(20)` alone
  has been sufficient in practice (STATUS's 30/30 clean result above is
  some evidence for the latter, but not a proof for every call shape).
