**Goal:** A dead isolated side must degrade the *relay outputs* only. It must
not degrade the node's liveness reporting. A host has to be able to tell "ORC
is present but cannot switch" apart from "ORC is intermittently gone", and
right now it cannot.

## Found by

`rigos-core` session, real hardware, 2026-08-30, while diagnosing a separate
`rigos-core` defect (BUG-033 there). Board on the bench harness with **the
isolated DC side disconnected** — ESP32-C3 and the CAN transceiver still
powered from USB, only the relay-driver rail dead, so the PCA9555 does not
ACK. CAN adapter on the Pi, `can0` up at 125 kbit/s, ERROR-ACTIVE.

Firmware not modified or reflashed to investigate. Everything below is
measured from the host side.

## Symptom

25-second passive capture on the Pi (listener only — sends nothing; the RPDO1
row is the Pi's own 1 Hz keepalive, shown for reference):

|     ID  | kind         |  n | mean gap | max gap |
|--------:|--------------|---:|---------:|--------:|
| `0x201` | RPDO1  -> n1 | 31 |   761 ms | 3304 ms |
| `0x281` | TPDO2  <- n1 |  3 |  9450 ms | 9451 ms |
| `0x701` | HB     <- n1 |  3 |  9450 ms | 9451 ms |

`kHeartbeatIntervalMs` is 1000 (`main.cpp:86`) and `kHealthCheckIntervalMs` is
1000 (`main.cpp:136`). Heartbeat and TPDO2 are emitted from the same `loop()`
pass and both stretched by the **same** factor, which is what identifies this
as a whole-loop stall rather than a fault in either emitter: `loop()` is
running at about **0.106 Hz**, roughly 9.4x slower than its intended period.

The node is not resetting and not dropping off — it transmits correctly, just
far too slowly.

## Consumer impact

`rigos-core`'s `orc_can.py` treats a `can_orc` bus as online purely on inbound
traffic — any Heartbeat or TPDO1 marks the node alive — against
`DEFAULT_HEARTBEAT_TIMEOUT_SECONDS = 3.0`, with **no hysteresis**. A 9.45 s
heartbeat period against a 3.0 s timeout means the host declares the bus
offline between every pair of heartbeats and online again on each arrival.

Observed effect: the ORC's health indicator oscillated green/red at roughly
1 Hz. In `rigos-core` that also triggered a second, unrelated defect that
cycled a *different* relay bus (fixed there as BUG-033); with that fixed the
flapping is cosmetic, but the underlying misreport is not — a host cannot
distinguish this from a genuinely intermittent node.

The ORC's own `checkControlActivityTimeout()` is also only evaluated once per
`loop()` pass, so under this stall the 5000 ms control-activity fail-safe is
checked every ~9.4 s instead of every ~1 s. It still fires, just late. Worth
stating explicitly because it is a safety-relevant timer being silently
stretched by an unrelated fault.

## Suspected mechanism — NOT yet confirmed on hardware

Two blocking paths run against an unresponsive PCA9555 and both plausibly
contribute, with a third compounding them. **The apportioning between them is
unmeasured** — do not treat the split below as established.

**1. The health-check reassert.** `reassertPca9555State()` (`main.cpp:211`)
issues **six** unconditional `pca9555WriteReg()` calls every
`kHealthCheckIntervalMs`. Its only guard is `if (!g_pca9555Present) return;`
at the top, and there is no re-check between the six writes — so once a cycle
begins, all six run even though the *first* failure already cleared
`g_pca9555Present` inside `pca9555WriteReg()` (`main.cpp:160`). Each is a
`Wire.endTransmission()` that must time out.

**2. The lazy re-probe on every command.** `requireRelayHardware()`
(`main.cpp:257`) calls `probeAndConfigurePca9555()` whenever
`g_pca9555Present` is false — which, per the above, it now permanently is. The
Pi's 1 Hz RPDO1 keepalive reaches `handleRpdo1()`, so a full probe-and-
configure sequence is attempted once per second, each one timing out again.

**3. Serial back-pressure, compounding both.** Every failed
`pca9555WriteReg()` prints a diagnostic (`main.cpp:152-154`). With BUG-002's
`Serial.setTxTimeoutMs(20)`, each such print can block up to 20 ms when
nothing is draining the USB CDC — and in this configuration nothing was. Six
writes per health check plus the probe path puts a non-trivial floor under the
loop period independent of the I2C timeouts themselves.

Note this is the **same symptom class as BUG-003** ("`loop()` appears to enter
a persistently slow state") but a different mechanism — that one was TWAI TX
backlog under fast commanding, this one is I2C to absent hardware. Worth
reading BUG-003's misdiagnosis trail before assuming which of the three paths
above dominates here; that bug's lesson was that a correctly-reasoned
mechanism can still not be the actual cause.

## Suggested direction (not a decided design)

The principle: **liveness must not sit behind relay-hardware I/O.**

- Back off the reassert once the chip is known absent, rather than retrying six
  writes every second — exponential backoff, or gate the whole health check on
  a much slower cadence while `g_pca9555Present` is false.
- Have `reassertPca9555State()` bail after its first failed write instead of
  running the remaining five against a chip already known to be gone.
- Rate-limit the failure diagnostic; one line per state change beats one line
  per failed write.
- Consider whether the heartbeat emitter should be driven from something that
  cannot be starved by loop work at all (a hardware timer or a separate task),
  which would make liveness structurally independent of any future blocking
  call, not just this one.

Whichever path is taken, the fault should still be *reported* — FR-002 already
covers signalling relay-hardware faults on the CAN wire, and this bug is an
argument for it: the host currently has no way to learn "PCA9555 absent"
except by inference from timing.

## Fix (2026-09-03)

Targeted the dominant of the three suspected contributors, per the numbers in
the "Suspected mechanism" section above: mechanism 2 (the lazy re-probe on
every RPDO1) is the only one of the three that scales with *how far behind
loop() has already fallen* — a stalled pass lets RPDO1 frames back up in the
TWAI RX queue (the host keeps sending its ~1 Hz keepalive regardless of
whether ORC is keeping up), and the next `loop()` pass drains the whole
backlog in one go, each frame re-triggering its own blocking I2C probe. That
is self-reinforcing in a way mechanisms 1 and 3 are not (both are one-shot
costs at the moment of the present→absent transition, not sustained ones) —
it is the best fit for a *sustained* ~9.4× slowdown across a 25 s capture,
not just a transition blip.

Three changes, `firmware/src/canopen_app/main.cpp`:

1. **`requireRelayHardware()`**: added a 1000 ms cooldown
   (`kPca9555ProbeRetryIntervalMs`, matching `kHealthCheckIntervalMs`'s
   existing cadence) between lazy re-probe attempts, tracked via a new
   `g_lastPca9555ProbeAttemptMillis`. Before this fix, every RPDO1 frame
   reaching `handleRpdo1()` re-triggered a full blocking I2C probe once the
   PCA9555 was absent — now at most one probe attempt per cooldown window,
   regardless of how many relay-touching calls (RPDO1, SET, GET, STATUS)
   arrive in that window. This directly breaks the compounding pileup: even
   in the worst case (a full TWAI RX queue's worth of backed-up RPDO1 frames
   drained in one `loop()` pass), only the first one within the cooldown
   actually blocks on I2C — the rest short-circuit on a `millis()` compare.
2. **`reassertPca9555State()`**: bails after the first failed write instead
   of unconditionally issuing all six (mechanism 1). `pca9555WriteReg()`
   already clears `g_pca9555Present` on any failure, so this only skips
   writes that would fail anyway once the first one has.
3. **`pca9555WriteReg()`**: its failure diagnostic now fires once per
   present→absent transition, over `printBestEffort()` (non-blocking), not
   once per failed write over a raw (blocking) `Serial.printf()` (mechanism
   3). Required a forward declaration since `printBestEffort()` is defined
   later in the file.

**Not changed**: the bigger architectural suggestion from this shard's
"Suggested direction" (driving the heartbeat emitter from something
structurally immune to `loop()` starvation, e.g. a hardware timer or a
separate task) — the three fixes above are a much smaller, more reviewable
diff, and per the analysis above they target the actual dominant mechanism
directly rather than working around it structurally. Worth revisiting if a
different starvation source ever produces the same symptom class again (this
is already the second time — see BUG-003).
