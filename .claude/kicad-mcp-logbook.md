## 2026-08-01 — firmware/ created: GPIO9 strapping question resolved, IO-level bring-up sketches added

**GPIO9-as-I2C-SCL-vs-BOOT-strap — resolved, safe.** Dispatched a research pass against Espressif's actual *ESP32-C3 Series Datasheet* v2.4 (not paraphrases/forum posts). Verdict: an idle-high I2C bus on GPIO9 does not conflict with the boot-mode strap read. The strap read is a one-shot latch completing within a fixed t_H ≥ 3ms window anchored to `CHIP_EN` release (§3, Table 3-2, Figure 3-1) — before firmware runs and before the IO MUX/GPIO Matrix has routed I2C onto GPIO8/9 at all (Table 2-1, §4.1.3.1). GPIO9's documented default is a weak pull-up (Table 3-1, bit=1=SPI boot); an external I2C pull-up reinforces that same direction, and the only way to break it is actively driving the pin low during the ~3ms window, which ordinary I2C (SCL low only during firmware-initiated clock pulses) structurally cannot do before the strap read completes. No published ESP32-C3 errata mention GPIO8/9/strapping/I2C. GPIO8 (SDA) is also a strapping pin, safe by the same timing argument, but defaults to floating rather than pulled — flagged as a minor caveat (a slave holding SDA low at its own power-on could theoretically coincide with `CHIP_EN` release) rather than a design problem. Full citation trail in `firmware/README.md`; `docs/subcircuit-capture-guide.md`'s MCU section rewritten to reflect this as resolved-with-citation, not left vague. Empirical confirmation on real hardware is still listed as an open item — this closed the static-analysis gap, not the "confirm on real hardware" one.

## 2026-08-01 — CAN protocol research: UART-vs-TWAI resolved, CANopen recommended

Research-only pass, dispatched to `can-interface`: resolve whether the current `firmware/src/uart_can_bringup` sketch's plain-UART-through-SN65HVD230 transport can actually do real CAN, and survey open application-layer standards for the "set 10 relay channels" payload before inventing anything custom. **No `hardware/*.kicad_sch`/PCB edits, no firmware code written** — checked `git status`/`git log` first and confirmed a parallel session has live, uncommitted edits to `hardware/orc.kicad_pro`/`orc.kicad_sch` (plus an untracked `hardware/relay_drive.kicad_sch`); this pass stayed entirely in `docs/` and this logbook.

**UART-vs-TWAI, resolved**: the ESP32-C3's TWAI (CAN) controller has no dedicated IO_MUX pin at all — Espressif's *ESP32-C3 Series Datasheet* v2.4 (Table 3-2) and the TRM's IO MUX/GPIO Matrix chapter confirm TWAI TX/RX are GPIO-Matrix-only signals, routable to any GPIO in firmware. GPIO21/GPIO20 (already wired to the SN65HVD230, already the pins `uart_can_bringup` uses) work exactly as well for real TWAI as for plain UART — **this is a firmware peripheral-config change (swap `HardwareSerial(1)` for the ESP-IDF/Arduino-ESP32 TWAI driver), not a hardware redesign.** Confirmed why the swap actually matters, not just that it's possible: ISO 11898-1's MAC-layer requirements — bitwise arbitration (each transmitter samples the bus mid-frame and yields on a lost bit), bit stuffing, CRC, and a receiver-driven ACK slot — all live in the CAN protocol controller (TWAI), not in the transceiver and not obtainable from a UART. TI's SN65HVD230 datasheet (SLOS346O §10.1) confirms it's a transparent physical-layer line driver only. A plain UART through it is a point-to-point differential serial link at CAN voltage levels, not CAN — no multi-drop arbitration, so two nodes keying up simultaneously get electrical contention, not resolved arbitration. Given ORC's own docs already anticipate a host (rigOS) plus potentially multiple ORC units on one bus (design-inputs.md's configurable-channel-mapping requirement, this task's multi-unit-fleet framing), that's exactly the shared-bus case real CAN arbitration exists for. **Recommendation: switch to the native TWAI controller before this ships** — flagged for the next firmware pass, not made here.

**Standards survey**: checked CANopen (CiA 301 COB-ID scheme + CiA 401 digital-I/O device profile), J1939, NMEA 2000 (PGN 127501/127502 binary switch-bank status/control — a genuinely close functional analog, closer culturally to ORC's RV/overlanding use case), DeviceNet (ODVA membership gate makes it less open than CiA's public knowledge-base + CANopenNode's OSS stack), and ISO-TP (not needed — every ORC payload identified, a 10-channel bitmask plus status/heartbeat, fits in one classic 8-byte CAN frame). **Recommended CANopen**, CiA 401-style: it's the only candidate pairing a real payload fit with both an open, freely-readable addressing scheme (CiA's public knowledge-base covers the predefined connection set well enough to implement without buying the paywalled CiA 301/401 PDFs — flagged medium-confidence on exact object-dictionary bit layout, high-confidence on the overall COB-ID/PDO/NMT architecture) and an existing OSS stack with a real ESP32 port (CANopenNode / CANopenNode_ESP32) — no authoritative ROM/RAM figure was found even in the maintainers' own issue tracker, so footprint-fits-4MB-flash/400KB-SRAM is a plausible estimate, not a confirmed number. The survey did **not** come up empty, so no custom frame format was designed.

**Concrete recommendation written up**: COB-ID allocation off CiA 301's predefined connection set (`0x200+NodeID` RPDO1 relay command, `0x180+NodeID` TPDO1 status, `0x700+NodeID` heartbeat, `0x080+NodeID` EMCY), a 2-byte RPDO1/TPDO1 bit layout (byte 0 = channels 1–8, byte 1 bits 0–1 = channels 9–10), and an explicit new open item: **ORC's board has no DIP switch or other config-input hardware for setting a per-unit node ID**, needed for the multi-unit-fleet case — flagged for the next hardware/firmware pass, not resolved here. ## 2026-08-02 — node-ID input: DIP switch, weight-labeled, not bit-labeled

User asked what to label the 4 node-ID pins, and flagged direct bit-number labeling (`BIT0-3`) as needlessly complex for a field installer. **Two decisions landed**: (1) component choice — a 4-position DIP switch instead of the 2.54mm header+shunt-jumper block assumed earlier today, since loose shunts are easy to lose during field service on a sealed-enclosure product (offered a rotary hex-switch alternative too, user picked DIP switch); (2) labeling convention — silkscreen (and the DIP switch's own printed numbering) reads `1 2 4 8` (decimal weight per position), not `BIT0-3` (bit index), so an installer sets a node ID by summing the ON positions rather than translating binary to decimal. ## 2026-08-05 — TPDO2 added: bus health/uptime, standards-conformant instead of overloading heartbeat

User asked what "NMT state byte" meant (heartbeat's payload) and, once explained, proposed embedding richer periodic data into the heartbeat message itself, configurable-frequency via a "RSDO." Walked through why that's a real CANopen conformance tradeoff — CiA 301 defines heartbeat as exactly 1 byte, DLC=1; a generic CANopen master or any of the standards-based switch panels from the earlier precedent survey would choke on or ignore a longer frame there. Recommended the spec-native alternative instead: **TPDO2**, the second of every CANopen node's four predefined transmit slots (ORC had only used TPDO1 so far). User agreed and picked "bus health + uptime" (not the fuller "+ reserved fault-bit placeholders" option) for its content via AskUserQuestion.

**Also corrected a terminology slip**: there's no "RSDO" — CANopen doesn't number SDO channels like PDOs; every node gets one SDO server (request `0x600+NodeID`, response `0x580+NodeID`) for object-dictionary reads/writes. **Designed**: TPDO2, COB-ID `0x280+NodeID`, DLC 8, default 1000ms/1Hz — byte 0 CAN-controller-state enum (design sketch, flagged as unverified against ESP-IDF's real `twai_state_t` until the firmware pass), bytes 1–2 TWAI TX/RX error counters, bytes 3–6 uptime-seconds as a `uint32` (sized generously — a 2-byte seconds field would wrap in under a day on a continuously-powered unit). Interval configurable via a standard SDO write to object `1801h` sub-index 5, persisted pragmatically to ESP32-C3 NVS on write rather than implementing the fuller `1010h`/`1011h` store/restore objects (flagged as a deferred nice-to-have, not designed).
