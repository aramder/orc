# ORC firmware

**Two kinds of content live here — don't conflate them.** The four `*_bringup`/`can_address_bringup` sketches exist to answer one narrow question — does the MCU pinout the hardware side has settled on actually work at the IO level? — before real application logic got written; see [`.claude/firmware-io-verification-prompt.md`](../.claude/firmware-io-verification-prompt.md) for that task. **`canopen_app` is different: it IS ORC's real application firmware** — actual relay control, driven from **either CAN or USB** against the same PCA9555 state, per [`docs/can-protocol-research.md`](../docs/can-protocol-research.md), [`docs/usb-bench-interface-spec.md`](../docs/usb-bench-interface-spec.md), and [`docs/features/FR-004.md`](../docs/features/FR-004.md). See its own section below.

**FR-004 (2026-08-10): USB control consolidated into `canopen_app`, the standalone `usb_bench` sketch retired.** Real bench testing the same day found `canopen_app`-only (CAN-only) and `usb_bench`-only (USB-only) too limiting for one board under active test with both interfaces in play — user's explicit ask: "I want to be able to drive from either CAN or USB interfaces." `usb_bench`'s protocol, findings, and fixes live on in `docs/features/FR-001.md` (marked superseded, not deleted) and in `canopen_app`'s own git history; there is no `[env:usb_bench]` anymore.

**Real ORC PCBs arrived and real-hardware testing started 2026-08-10.** Boards came back from fab, populated, and are being bench-tested for the first time. First real result, `i2c_scanner` on a powered, fully-wired ORC PCB: idle bus reads HIGH/HIGH (clean pull-ups, no strapping fault), CAN address bank correctly reads `0` with all four DIP switches open, and **the PCA9555 ACKs at 0x20** — the first-ever confirmation the ADuM1250 I2C isolator + PCA9555 chain works as designed on real fabricated hardware, not just static analysis. This also empirically confirms the GPIO2 boot-strap safety analysis (see "Configurable CAN node address, as-fabbed" below) for the DIP-switches-open position; the closed/HIGH position on GPIO2 hasn't been walked yet. SN65HVD230/real-CAN-bus testing hasn't happened yet as of this pass. **Still true for now**: don't read "runs on a generic ESP32-C3 dev kit" (below) as equivalent to "verified on the real ORC board" — but as of today, real-board testing is actively underway, replacing that caveat's earlier "no board in hand at all" state. Update this section as each sketch gets its first real-PCB run, don't leave it reading like nothing has changed once it has.

**History, for context**: the board was sent to fab 2026-08-02 and came back some time before this pass. All five firmware environments (`i2c_scanner`, `pca9555_bringup`, `uart_can_bringup`, `can_address_bringup`, `canopen_app`) build successfully against the `esp32-c3-devkitm-1` stand-in board. Two of them (`i2c_scanner`, `uart_can_bringup`) also ran live on a bare, generic ESP32-C3 dev kit before any ORC PCB existed — see "Real-hardware run, 2026-08-01" below for exactly what that did and didn't confirm (nothing PCA9555/SN65HVD230-related). `canopen_app` (as `usb_bench` too, before it was retired into `canopen_app` by FR-004) found and fixed a real bug (halting `setup()` before relay-agnostic functionality ACKed, taking bus-agnostic functionality down with it — BUG-001) on a bare devkit before any ORC PCB was available. **Firmware's pin assignment was corrected once, same day it was sent to fab** — see "CAN node address, as-fabbed" below; the schematic is the source of truth firmware must match, not the other way around.

## Board stand-in

`platformio.ini` targets PlatformIO's `esp32-c3-devkitm-1` board definition. This is a **stand-in**, not the final hardware — the actual target is a generic, widely-cloned "ESP32-C3 Super Mini"-class board (bare ESP32-C3FN4 die, 4MB flash, no PSRAM, USB-C, 2×7-pin THT headers) with no single confirmed SKU yet. `esp32-c3-devkitm-1` is electrically close enough (same chip class) to compile and flash against for IO-level bring-up; swap it for a real board definition once a specific listing is bought and its exact silkscreen/pin breakout is confirmed.

## Pin assignment under test

Per `hardware/mcu.kicad_sch` (U7, as-fabbed) and `docs/subcircuit-capture-guide.md`'s MCU section — full 13-GPIO "Super Mini" header pinout (GPIO0-10, GPIO20, GPIO21):

| Function | Pins |
|---|---|
| I2C (SDA/SCL) | GPIO8 / GPIO9 |
| UART (TX/RX, to SN65HVD230) | GPIO21 / GPIO20 |
| CAN node address (NODE_ID0-3) | GPIO0 / GPIO1 / GPIO2 / GPIO3 |
| Spare (unused) | GPIO4-7 (JTAG-default), GPIO10 |

## Configurable CAN node address, as-fabbed

4-bit node address (0-15), read directly by the ESP32-C3 — deliberately **not** through the PCA9555, since address-select logic belongs on the MCU's own non-isolated Domain A side, not across the ADuM1250 isolation barrier onto Domain B where the PCA9555 lives. Shared logic lives in `lib/orc_can_addr/` and is linked into every sketch below, each printing the current reading at startup.

**Wiring**: external 10kΩ pulldown to GND per bit, switch/jumper to 3V3 per bit — open=0 (LOW), closed=1 (HIGH). Plain `INPUT` mode in firmware (no internal pull requested); the external 10k dominates the ESP32-C3's own internal weak pull resistors (~45kΩ typ either direction per the datasheet) regardless of their state, so there's nothing to fight.

**Pins actually built: GPIO0, GPIO1, GPIO2, GPIO3 — corrected after the fact, not the original plan.** The initial pick (documented 2026-08-02, before the board went to fab) was GPIO0/1/3/10, specifically chosen to avoid GPIO2 since it's one of the ESP32-C3's three strapping pins. **That was never what got built.** The as-fabbed schematic (`hardware/mcu.kicad_sch`, U7) wires `NODE_ID0`..`NODE_ID3` to a contiguous `IO0`..`IO3` block — which includes GPIO2 and doesn't use GPIO10 at all. This firmware has been corrected to match the real board; the schematic is the source of truth here, not the firmware plan.

**GPIO2 strapping safety — re-verified with real rigor since it's now load-bearing on a board that's already at fab, not just a design preference to weigh.** The ESP32-C3's full strapping-pin set is exactly {GPIO2, GPIO8, GPIO9} (Espressif *ESP32-C3 Series Datasheet* v2.4, Table 3-1/3-2/3-3). Table 3-3 "Chip Boot Mode Control" has exactly two rows:

| Boot Mode | GPIO2 | GPIO8 | GPIO9 |
|---|---|---|---|
| SPI Boot (normal) | Any value | Any value | 1 |
| Joint Download Boot | 1 | 1 | 0 |

— with the table's own footnote stating plainly: *"GPIO2 actually does not determine SPI Boot and Joint Download Boot mode, but it is recommended to pull this pin up due to glitches."* This board's I2C pull-up (R21, `SCL_A`, 10kΩ — see `docs/subcircuit-capture-guide.md`'s I2C Isolator section) holds **GPIO9 = 1 at every reset**, which is the sole determinant of the SPI-Boot row. Both address-switch positions on GPIO2 (LOW via the external 10k pulldown when open, HIGH when closed) land in that same SPI-Boot row regardless — GPIO2's column is "Any value" whenever GPIO9=1, and GPIO9=1 is guaranteed here. No published ESP32-C3 errata mention GPIO2 (checked directly against Espressif's chip errata index, not assumed absent by analogy to GPIO8/9). **Verdict: safe as fabbed, no rework needed.** Espressif's own generic recommendation to add a pull-up on GPIO2 (to guard against glitches on a *floating* GPIO2 in designs where GPIO9 isn't independently pinned) doesn't apply here in the same way, since this design's own pull-down plus GPIO9's independent pull-up together determine the outcome regardless of GPIO2's transient state.

GPIO0/1/3 are also ADC1_CH0/CH1/CH3 — irrelevant here since they're used purely as digital inputs, not sampled by the ADC. GPIO10, spare in this design, was the original plan's bit3 pin but isn't actually wired to anything address-related on the real board.

## The GPIO9 strapping question — resolved

GPIO9 is the ESP32-C3's BOOT strapping pin (default weak pull-up = normal SPI-flash boot) and is also assigned as I2C SCL. **Datasheet analysis verdict: safe, no conflict.** Full reasoning and citations now live in `docs/subcircuit-capture-guide.md`'s MCU section; summary:

- The boot-strap read is a one-shot latch completing within a fixed **t_H ≥ 3 ms** window anchored to `CHIP_EN` release (Espressif *ESP32-C3 Series Datasheet* v2.4, §3, Table 3-2, Figure 3-1) — before firmware runs and before the IO MUX/GPIO Matrix has routed the I2C peripheral onto GPIO8/9 at all (same datasheet, §4.1.3.1; Table 2-1 shows GPIO9's at-reset/after-reset state as plain `IE, WPU`, not an I2C pin).
- An idle-high I2C bus **reinforces** GPIO9's documented default pulled-up strap value (Table 3-1: GPIO9 default = weak pull-up, bit=1=SPI boot); external pull-ups are the datasheet's own documented mechanism for setting strap state and are not flagged as a hazard when they match the default direction.
- The only way to disturb the strap read is to actively drive GPIO9 **low** during the ~3 ms window — ordinary I2C only pulls SCL low during active clock pulses initiated by firmware, which cannot run before the strap read has already completed and been latched.
- No published ESP32-C3 errata mentions GPIO8/GPIO9/strapping/I2C (checked against Espressif's official chip errata index).
- GPIO8 (SDA) is also a strapping pin (chip-boot-mode + UART-print-control), defaults to **floating** (not pulled), and is safe by the same timing argument. One real caveat carried into the docs: GPIO8's floating default means if some other I2C slave on the bus holds SDA low during its own power-on reset at the same instant as the ESP32-C3's `CHIP_EN` release, that could unintentionally affect the GPIO8 strap read (Table 3-3: only matters if GPIO9 also reads 0 at that instant) — a general I2C power-sequencing caution, not specific to this design, and not a reason to reassign pins.

No pin reassignment was made. If a strapping-pin-free I2C pair is ever wanted for unrelated reasons, GPIO4/5 or GPIO6/7 avoid the {GPIO2, GPIO8, GPIO9} strap set but carry JTAG (MTMS/MTDI/MTCK/MTDO) as their IO-MUX default association — a different caution category, and not verified against this design's specific "Super Mini" header breakout.

## SN65HVD230 UART baud rate

The SN65HVD230 CAN transceiver has **no UART framing requirement of its own** — it's a transparent ISO 11898-2 physical-layer line driver, not a UART part (TI *SN65HVD230/1/2* datasheet, SLOS346O, rev. April 2018: §7 Pin Functions, §10.1 Overview). Its datasheet gives a "designed for data rates up to 1 Mbps" target (Features, p.1) and hard propagation-delay/rise-time limits in high-speed mode (§8.7–8.9, tens-to-~135 ns depending on the parameter) — not a baud spec. `uart_can_bringup` picks 500 kbps as a conventional round number comfortably under that ceiling; it is a firmware-side choice, not a transceiver requirement. **Caveat**: those propagation-delay numbers assume RS (slope-control) tied to ground for high-speed mode — if ORC's board leaves RS in slope-control mode via a resistor instead, propagation delay balloons (up to ~1200 ns typ at 100 kΩ RS per the datasheet's switching-characteristics table) and would cap the practical rate well below 1 Mbps. Confirm ORC's actual RS pin configuration before assuming the 1 Mbps ceiling applies.

## Real-hardware run, 2026-08-01

A bare, generic ESP32-C3 dev kit (chip ID reported by `esptool`: **ESP32-C3 QFN32, silicon revision v0.4**, 4MB embedded flash, native USB-Serial/JTAG, MAC `3c:84:27:af:48:fc`) was connected to the machine this session ran on, with **nothing else wired to it** — no PCA9555, no SN65HVD230, no I2C pull-ups beyond whatever the bare board itself has. This is not ORC's board and does not exercise the PCA9555 or CAN-transceiver bring-up logic; it confirms the ESP32-C3 IO-level pieces (I2C peripheral init, UART peripheral init, USB console) actually run on real silicon of the correct chip family.

**Bug found and fixed by this test, not cosmetic**: the stock `esp32-c3-devkitm-1` board definition does not enable USB-CDC-on-boot, so Arduino's default `Serial` console silently bound to UART0 on **GPIO21(TX)/GPIO20(RX) — the exact pins this design assigns to the CAN-transceiver UART** — instead of the native USB-Serial/JTAG port. First flash produced zero console output for this reason. Fixed in `platformio.ini` with `-D ARDUINO_USB_MODE=1 -D ARDUINO_USB_CDC_ON_BOOT=1`, which routes `Serial` onto native USB and frees GPIO21/20 exclusively for the CAN UART (`Serial1`) as intended. Worth carrying into whatever final board definition replaces the `esp32-c3-devkitm-1` stand-in — the same collision would otherwise resurface silently on real ORC hardware.

- **`i2c_scanner`**: flashed and ran live. Correctly reported no ACKs on the bus (expected — nothing is wired to GPIO8/9 on this bare dev kit) and printed the idle-bus-level check without error. Confirms the I2C peripheral initializes and runs on real hardware; does not confirm anything about the PCA9555 (not attached).
- **`uart_can_bringup`**: flashed and ran live. Baseline (nothing jumpered) correctly showed "RX: nothing received" every cycle. With GPIO21 (TX) physically shorted to GPIO20 (RX) by a jumper wire, **loopback verified end-to-end**: every `ORC-BRINGUP-<counter>` pattern sent came back byte-for-byte (22 bytes including `\r\n`), one-to-one, no drops or corruption, at 500 kbps. Confirms UART1 on these exact pins transmits and receives correctly on real silicon; does not confirm anything about the SN65HVD230 or a real CAN bus (neither present).
- **`pca9555_bringup`**: not run this session — no PCA9555 is attached to this dev kit. By design it halts cleanly at the "PCA9555 did not ACK" check rather than doing anything unsafe without the part present; still only build-verified, not run.

## Real-hardware run, 2026-08-10 — first test against an actual ORC PCB

Real, populated, powered ORC PCBs are in hand as of this pass — the first real-hardware test against the design this whole directory has been targeting, not a bare devkit stand-in. First board wired up and tested via `i2c_scanner`, flashed to a bare ESP32-C3 module wired to the board (COM7, `esptool`-reported chip ID: ESP32-C3 QFN32 silicon revision v0.4, MAC `AC:27:6E:45:90:98` — a different unit than the 2026-08-01 run's `3c:84:27:af:48:fc`).

Live boot output:

```
=== ORC bring-up: I2C bus scanner ===
SDA=GPIO8  SCL=GPIO9  expected PCA9555 addr=0x20
CAN node address: 0 (bits 3210 = 0000, pins GPIO3/2/1/0)
Idle bus levels before Wire.begin(): SDA(GPIO8)=HIGH  SCL(GPIO9)=HIGH
Both lines read HIGH at idle -- normal.

Scanning I2C bus (addresses 0x03-0x77)...
  ACK at 0x20  <-- expected PCA9555 address
1 device(s) found.
```

**Confirms, for the first time on real fabricated hardware, not static analysis or a bare-devkit substitute**:
- **PCA9555 ACKs at 0x20.** The ADuM1250 I2C isolator + PCA9555 chain works as designed, crossing the Domain A/B isolation barrier for real.
- **GPIO2 boot-strap safety, empirically confirmed for the DIP-switches-open position**: bus idles HIGH/HIGH, board boots and runs normally with GPIO2 (a strapping pin) held at its address-bank LOW/open state. This is the predicted-safe outcome from the Table 3-3 datasheet analysis (see "Configurable CAN node address, as-fabbed" below), now observed on real silicon instead of just argued from the datasheet. **Not yet walked**: the CLOSED/HIGH position on GPIO2 specifically — the analysis says it lands in the same safe boot-mode row, but that position hasn't been physically tested yet.
- **CAN node address bank reads correctly**: `0` with all four DIP switches open, matching the external-pulldown design (open = LOW = 0).

**`pca9555_bringup` confirmed shortly after, same session**: flashed to the same board, ran its full 10-channel walking pattern, user cross-checked every channel with a DMM in continuity mode on the coil harness pins — all 10 correct, no swaps, no misses. First end-to-end confirmation of the routing-driven channel-mapping table (schematic → `orc_relay_map.h` → real silicon → real coil driver → real relay) on actual hardware, not just internal firmware/schematic consistency. Full writeup: `pca9555_bringup`'s own section below.

**Real hardware fault found and fixed, same session — mechanical, not electrical design.** A second board (or second connection session) showed relays only weakly actuating (faint click, not enough force to close contacts) and I2C throwing driver-level errors partway through the run. Chased through several hypotheses (PCA9555 brownout-reset from coil inrush, then a wedged I2C bus) before the user found the real cause by physical inspection: **the harness connector's unshrouded THT pins were shorting against the metal enclosure chassis.** One electrical fault, two symptoms — the short sagged shared supply rail(s) under coil-switching current, starving coil drive and glitching the PCA9555's own logic supply at the same time. Not a coil-supply sizing problem, not a firmware bug. Full writeup and the follow-up mechanical-clearance item: `docs/circuit-draft.md`'s "Harness connector — measured pinout" section. `pca9555_bringup`'s own periodic-PCA9555-reconfigure defensive hardening (added while chasing this) stayed in as cheap insurance; an I2C bus-recovery attempt added at the same time was tested live, found not to actually work on this Arduino-ESP32 core's I2C driver, and removed rather than left in as broken code claiming success — see the sketch's own comments for the full chase.

**FR-004, same session, later**: user asked for USB control to be built into `canopen_app` itself rather than living only in the separate `usb_bench` sketch, so relays could be driven from either interface against the same board. `usb_bench` retired; its protocol/fixes consolidated into `canopen_app` — see that section below and `docs/features/FR-004.md`. `canopen_app` (with USB now built in) then drove all 10 channels ON over USB directly on this real board: real coil current confirmed (0.47A at 12V input, matching the ~0.45A design target almost exactly), all 10 relays audibly/visibly actuated. One test-tooling false alarm along the way, not a firmware bug: a Python test script's `pyserial.Serial.close()` call toggled the native-USB-CDC auto-reset lines (the same RTS mechanism `esptool` uses for flashing) and rebooted the chip, which looked like "the relays turned off after ~1 second" but was actually a full reset wiping all state back to boot defaults — confirmed by re-running the same test with the port kept open for 15+ seconds: heartbeat counted up smoothly the whole time, zero reboots, all 10 channels held.

**`canopen_app` CAN side, tested and a real bug found and fixed, 2026-08-10.** Bench-tested end-to-end against real hardware (real ORC board, Jhoinrch RH-02 USB-CAN adapter, `tools/relay_toggle_test.py`'s 1-10 sweep + all-on): the RPDO1 command path worked correctly from the first run (relays physically confirmed clicking through in sequence), but TPDO1 confirmation was unreliable in a specific pattern — roughly every other TPDO1 missing, survivors reporting the previous step's mask. Root cause, found by reading the Arduino-ESP32 native-USB-CDC (`HWCDC`) driver source directly, not assumed: `handleRpdo1()` logs the incoming RPDO1 via `Serial.printf()` *before* `applyRelayCommand()` sends TPDO1, and a blocking native-USB write can stall up to ~2000ms (20 retries × 100ms default `tx_timeout_ms`) if the physical USB link is up but nothing drains the ring buffer — longer than the test's 2s confirm window, and nothing to do with CAN bus health (a bus-health theory was tested first and directly refuted: TEC held at 0 for 10+ seconds through a full sweep, termination confirmed correctly populated, symptom unchanged). Fix: `setup()` now calls `Serial.setTxTimeoutMs(20)`, bounding any blocking `Serial` write to ~200ms. Re-verified against the reflashed board: 12/12 sweep steps confirmed. Full investigation trail: `.claude/tpdo1-lag-investigation-prompt.md` (gitignored, local only).

`uart_can_bringup` itself has not been separately re-run against this same setup — `canopen_app` (the real application firmware) has now been validated on both CAN and USB against real hardware, `uart_can_bringup` (an earlier bring-up-only sketch) is superseded for that purpose.

## Sketches

Each sketch is its own PlatformIO environment (separate, individually-flashable — not one monolithic test). Build/flash one at a time:

```
pio run -e i2c_scanner -t upload -t monitor
pio run -e pca9555_bringup -t upload -t monitor
pio run -e uart_can_bringup -t upload -t monitor
pio run -e can_address_bringup -t upload -t monitor
pio run -e canopen_app -t upload -t monitor
```

(Run from this `firmware/` directory. `-t monitor` opens the serial console at 115200 baud after flashing; omit it to just build+flash.)

### `i2c_scanner` ([src/i2c_scanner/main.cpp](src/i2c_scanner/main.cpp))

Scans the I2C bus (addresses 0x03–0x77), reports any device that ACKs — specifically flags 0x20, the PCA9555's address (A0–A2 strapped low). Before starting the I2C peripheral, reads SDA/SCL as plain GPIO to report whether the bus idles HIGH (normal) or LOW (a real fault — stuck bus, missing pull-up, or a device holding the line; the classic symptom anyone chasing a strapping-conflict theory would look for, though per the analysis above it isn't expected to be one here).

### `pca9555_bringup` ([src/pca9555_bringup/main.cpp](src/pca9555_bringup/main.cpp))

Configures the PCA9555 as 10 outputs and walks a single HIGH bit across channels 1–10 in sequence, 500 ms per step, using the **real, schematic-confirmed channel-to-register mapping** in `lib/orc_relay_map/`. Intended for a scope probe or a per-channel LED jig to visually confirm addressing and pin mapping once hardware exists. **Corrected 2026-08-05**: an earlier version of this sketch assumed channels 1-8 were sequential on Port0 (whole byte) with channels 9-10 on Port1's low 2 bits — that assumption was wrong. `docs/subcircuit-capture-guide.md`'s "Channel mapping" table (read directly off `hardware/i2c_expander.kicad_sch`) shows the real mapping is routing-driven and non-sequential, spanning both ports (e.g. channel 1 = Port1 bit0, channel 2 = Port0 bit7, channel 10 = Port0 bit3). "Channel 3" in this sketch's output now means the schematic's actual channel 3.

**Real-hardware confirmed, 2026-08-10**: flashed to a real, powered ORC PCB and run through its full walking pattern. User followed along with a DMM in continuity mode on the coil harness pins and confirmed all 10 channels click in the correct physical position, matching the printed `Channel N HIGH` output exactly — no swaps, no misses. This is the strongest verification the channel-mapping table has had: schematic → `orc_relay_map.h` → real silicon → real coil driver stage → real relay, checked end to end. Full writeup: `docs/subcircuit-capture-guide.md`'s "Channel mapping" section.

### `uart_can_bringup` ([src/uart_can_bringup/main.cpp](src/uart_can_bringup/main.cpp))

Configures UART1 at 500 kbps on GPIO21(TX)/GPIO20(RX) — the pins wired to the SN65HVD230 — sends a counted test pattern (`ORC-BRINGUP-<counter>`) once per second, and reports whatever arrives on RX within a 500 ms window. Useful for a bench loopback test (jumper TX to RX, or through the transceiver with CAN_H/CAN_L looped/terminated) before a real bus exists, and for testing against a second node once one does. This is raw UART bytes through the transceiver, not CAN-protocol-framed traffic.

### `can_address_bringup` ([src/can_address_bringup/main.cpp](src/can_address_bringup/main.cpp))

Reads the 4-bit CAN-address bank (GPIO0/1/2/3, see "Configurable CAN node address, as-fabbed" above) and prints the resulting 0-15 value once per second, along with each individual bit. Intended for a bench check: walk all 16 switch combinations and confirm each one reads back correctly before trusting the scheme in the field. The other bring-up sketches also call the same `orcPrintCanAddress()` helper (from `lib/orc_can_addr/`) once at startup, so whichever one is running, the console banner always states which node address the board is currently set to — useful as soon as more than one ORC unit might be on a bench or bus at once.

## `canopen_app` — application firmware: relay control from CAN or USB

**This is real relay-control firmware, not a bring-up test.** Implements the full CAN protocol specified in `docs/can-protocol-research.md`: real CAN (TWAI, not the `uart_can_bringup` UART scheme), 125 kbit/s, node-ID-based addressing (reuses `lib/orc_can_addr` unchanged), and four messages — RPDO1 (relay command), TPDO1 (relay status), TPDO2 (bus health/uptime), Heartbeat — plus one minimal SDO object for TPDO2's configurable send interval. **FR-004 (2026-08-10) added a second, equally real control path**: the same plain-ASCII USB protocol `docs/usb-bench-interface-spec.md` defines, previously its own separate `usb_bench` sketch (now retired) — `PING`/`VERSION`/`SET`/`GET`/`STATUS` plus unsolicited `HB`/`STATE` lines, driving the *same* PCA9555 state as CAN does. Real ORC boards are in hand and under active bench test as of 2026-08-10 (see the top status note above) — this firmware found and fixed a real-hardware bug (BUG-001, same halt-on-missing-PCA9555 class `usb_bench`'s FR-001 also hit) on a bare devkit before an ORC PCB was available, and has since driven all 10 real relays over USB on the real board (0.47A real coil current, matching the ~0.45A design target).

```
pio run -e canopen_app -t upload -t monitor
```

**Transport**: ESP-IDF/Arduino-ESP32's native TWAI driver (`driver/twai.h`), `tx_io=GPIO21`, `rx_io=GPIO20` — the same physical pins `uart_can_bringup` uses, but a genuinely different on-chip peripheral (TWAI vs UART1), per `can-protocol-research.md`'s UART-vs-TWAI resolution: TWAI has no dedicated IO_MUX pin on the ESP32-C3, it's GPIO-Matrix-routable to any pin, so this is a firmware-only change with zero schematic impact. Given separate `ORC_TWAI_TX_PIN`/`ORC_TWAI_RX_PIN` build flags (same values as `ORC_UART_TX_PIN`/`RX_PIN`) rather than reusing the UART-named constants, since reusing them here would misleadingly suggest this sketch is still UART-based. **Bitrate: 125 kbit/s, locked** (`TWAI_TIMING_CONFIG_125KBITS()`) — per `can-protocol-research.md`'s "Bus bitrate" section; don't change this without updating that doc and coordinating with `rigos-core`'s FR-059, which is being built against this exact value from the host side.

**Node ID**: read via `lib/orc_can_addr` at startup, unchanged from the bring-up sketches. **If the address reads 0** (all 4 DIP-switch positions open — not a valid CANopen node ID, CiA 301 requires 1-127), CAN is disabled for that session (no heartbeat, TPDO1/TPDO2, RPDO1, or SDO) rather than silently joining the bus non-conformantly — **but the sketch keeps running and USB control still works normally**, per FR-004's proactive fix (see below): a missing node ID used to halt the *entire* sketch before this pass, which would have taken USB down with it too, defeating the whole point of having two independent interfaces.

**Messages implemented** (COB-ID = base + NodeID, see `can-protocol-research.md` for the full spec):

| Message | COB-ID | Direction | What it does |
|---|---|---|---|
| RPDO1 | `0x200+NodeID` | host → ORC | 2-byte relay command (byte0=channels 1-8, byte1 bits0-1=channels 9-10) — this is the **wire protocol's** channel numbering, translated to real PCA9555 register bits via `lib/orc_relay_map/`'s schematic-confirmed, routing-driven mapping (channels are NOT sequential Port0-then-Port1 bits — see `pca9555_bringup`'s section above for the same correction). `orc_canopen.h` only handles the 2-byte-payload ↔ 10-bit-channel-mask conversion; `orc_relay_map.h` handles channel-mask ↔ PCA9555-register-value, kept as two separate, composable translation steps. |
| TPDO1 | `0x180+NodeID` | ORC → host | 2-byte applied relay status, sent after **any** real applied-state change — not only ones RPDO1 itself caused (FR-004: a USB `SET` command now also triggers a TPDO1 broadcast, so a CAN listener's view of applied state stays truthful regardless of which interface changed it). Read back from the PCA9555's Input Port registers (which reflect actual driven pin level even for output-configured pins) rather than just echoing the command — real command-vs-applied confirmation, even without current sensing. |
| TPDO2 | `0x280+NodeID` | ORC → host, periodic (default 1000ms, SDO-configurable) | 8-byte bus health/uptime: byte0 CAN-controller-health enum, bytes1-2 TWAI TX/RX error counters, bytes3-6 uptime-seconds (`uint32` little-endian). Byte-0 enum and error-counter width were both flagged in `can-protocol-research.md` as unverified design sketches — **both confirmed this pass against ESP-IDF's actual `driver/twai.h`** (see that doc's TPDO2 section for the citation), implemented in `lib/orc_canopen/orc_canopen.h`. **Uptime bug found and fixed in 2026-08-05 review**: the field was originally computed from `millis()`, which wraps at ~49.7 days and would have silently reset the reported uptime on any continuously-powered unit — now uses `esp_timer_get_time()` (64-bit microseconds-since-boot), which doesn't have that problem. |
| Heartbeat | `0x700+NodeID` | ORC → host, periodic, fixed 1000ms | 1-byte NMT state. Sends Boot-up (0) once at the end of `setup()`, then Operational (5) on every subsequent periodic send — a fixed "Boot-up once, then always Operational" NMT posture, no Stopped/Pre-operational transitions implemented, stated explicitly rather than silently skipped. |
| SDO (minimal) | rx `0x600+NodeID`, tx `0x580+NodeID` | host ↔ ORC | Recognizes exactly one (index, sub-index) pair — `1801h`/`5`, TPDO2's event timer in milliseconds — and aborts (standard CiA 301 abort codes) anything else. Not a general SDO server, per the task's explicit scope. A successful write applies the new interval immediately and persists it to the ESP32-C3's NVS (`Preferences`, namespace `orc_cfg`, key `tpdo2_ms`) so it survives a power cycle; default 1000ms if nothing's been persisted yet. |

**Control-activity fail-safe, now unified across both interfaces (FR-004)**: if neither CAN (RPDO1) nor USB (any command) produces real activity within a threshold, all channels are de-energized rather than holding last state — per `can-protocol-research.md`'s explicit safety recommendation, now extended to cover USB too. **Two thresholds, not one, and picked by which interface was most recently active, not a single shared clock**: 5000ms after CAN activity (the original RPDO1-timeout value — not a cited spec value, picked as 5x the TPDO2/Heartbeat default period), 30000ms after USB activity (ported from `usb_bench`/FR-001's own reasoning — a human typing pauses far longer than a machine's command cadence). A naive single shared last-activity timestamp checked against both thresholds does NOT correctly implement "either interface's activity postpones both" — since 5000 < 30000, the shorter threshold always fires first on a shared clock, making the 30s USB grace period unreachable dead code. Tracking *which* interface supplied the most recent activity and selecting the threshold from that avoids this: a pure-CAN session keeps the strict 5s fail-safe, a pure-USB session gets the full 30s grace, and either interface's activity postpones the other's countdown. See `docs/features/FR-004.md` for the full reasoning.

**TWAI bus-off recovery**: added in the 2026-08-05 review pass — was missing entirely from the original implementation. ESP-IDF's TWAI driver does not recover from bus-off on its own: `twai_initiate_recovery()` must be called explicitly, and even after recovery completes the driver lands in `STOPPED`, not `RUNNING` — `twai_start()` must be called again to actually resume. Without this, a bus fault would be correctly *reported* via TPDO2's health byte (`BUS_OFF`/`RECOVERING`) but never actually recovered from, needing a physical power-cycle. `checkTwaiRecovery()` runs on a fixed 1-second cadence (independent of TPDO2's own SDO-configurable interval, deliberately) and handles both the `twai_initiate_recovery()` call and the follow-up `twai_start()`.

**Not implemented, by explicit scope choice, not oversight**: EMCY (`0x080+NodeID`) — flagged in the spec as a stretch goal, skipped this pass. Full `1010h`/`1011h` CANopen store/restore objects — the NVS auto-persist-on-write above satisfies "survives a power cycle" without them; a reasonable later addition if ORC ever needs to interoperate with a generic CANopen config tool expecting the standard mechanism specifically. No general-purpose CANopen stack or object dictionary — the message set is small and fully specified, hand-rolled directly on the TWAI driver per the task's explicit instruction not to pull in a library (e.g. CANopenNode) for this.

**Shared libraries**: `lib/orc_canopen/orc_canopen.h` — pure wire-protocol encode/decode helpers (COB-ID arithmetic, RPDO1/TPDO1 2-byte-payload ↔ 10-bit-channel-mask, TPDO2 payload packing, the one-object SDO wire format). `lib/orc_relay_map/orc_relay_map.h` — the real, schematic-confirmed channel-mask ↔ PCA9555-register-value mapping, shared with `pca9555_bringup` (see its section above). Splitting these two translation steps (protocol bytes ↔ channel mask, channel mask ↔ PCA9555 registers) into separate libs is deliberate — it's what let the routing-driven mapping bug get caught and fixed in one place without touching the wire-protocol format at all. Neither lib makes TWAI/I2C/NVS calls of its own; `canopen_app/main.cpp` owns the actual peripherals and runtime loop. Both header-only, no `.cpp` — everything's a small `inline` function.

### USB control (FR-004, formerly the standalone `usb_bench` sketch)

Same physical native USB-C port already wired for flashing, same plain-ASCII protocol `docs/usb-bench-interface-spec.md` defines — **now built into `canopen_app` directly**, driving the same PCA9555 state CAN does, not a separate binary. ORC's resolved control-path decision (`docs/design-inputs.md`) — CAN, exclusively, in the field — is unchanged; USB remains explicitly a bench/dev interface, just one that now lives in the real firmware instead of a throwaway sketch.

**Transport/framing**: native USB CDC-ACM (`Serial`), same `ARDUINO_USB_MODE`/`ARDUINO_USB_CDC_ON_BOOT` build flags every sketch here sets. Plain ASCII, one command/response per line, `\n`-terminated (`\r` tolerated/stripped), 128-byte max line length (`ERR LINE_TOO_LONG` past that), case-insensitive commands. Point-to-point by construction — no NodeID concept on the USB side, unlike CAN.

**Commands** (exactly per the spec):

| Command | Response | Notes |
|---|---|---|
| `PING` | `PONG <fw_version>` | Liveness + identify. Works even with CAN unjoined or no PCA9555 present. |
| `VERSION` | `VERSION <fw_version> <build_date>` | Fuller build info. |
| `SET <ch> ON\|OFF` | `OK SET <ch> ON\|OFF` or `ERR <code>` | `<ch>` is 1-10. Goes through the same `applyRelayCommand()` RPDO1 uses — a CAN listener sees a TPDO1 for this too. |
| `GET <ch>` | `STATE <ch> ON\|OFF` or `ERR <code>` | Applied state, PCA9555 Input Port read-back, not an echo of the last command. |
| `STATUS` | `STATUS <10-char 0/1 string>` | Channel 1 first, e.g. `STATUS 0010000000` = channel 3 on. |

**Unsolicited lines**: `HB <uptime_ms>` every 1000ms (always, regardless of whether CAN is joined); `STATE <ch> ON\|OFF` on every real applied-state change from *either* interface (CAN RPDO1, USB SET, or the fail-safe) — one shared read-back feeds both this and CAN's TPDO1 broadcast, so neither interface's view of reality can silently drift from the other's.

`SET`/`GET`/`STATUS` attempt a lazy on-demand PCA9555 re-probe if hardware wasn't previously known-present (ported from `usb_bench`/FR-001), returning `ERR NO_RELAY_HARDWARE` only if that also fails — same treatment `handleRpdo1()` now gets too, which it didn't have before this consolidation (BUG-001 only stopped it from halting the whole sketch, it never re-probed after boot).

**Known limitation, documented not silently accepted (FR-004)**: this file's Serial output was always a human debug log (RPDO1 dumps, TWAI errors, SDO writes, etc.), not the strictly line-clean protocol `usb_bench` alone was. That debug prose is now interleaved with the real protocol lines on the same port — a host-side parser MUST tolerate/ignore unrecognized lines, extending the spec's existing "check first token" robustness requirement to cover diagnostic prose too, not only other protocol lines.

**Real-hardware gotcha, not an ORC feature**: closing a serial connection (e.g. `pyserial`'s `Serial.close()`) can toggle the DTR/RTS lines the native-USB-CDC auto-reset mechanism watches — the same one `esptool` uses to flash without a physical BOOT button — and trigger a full chip reboot, wiping all state including energized relays. Confirmed live 2026-08-10: a test script's port-close looked exactly like "relays turned off after ~1 second," but a 15-second open-port re-test with the same commands showed zero reboots and all channels holding the whole time. Any host-side driver against this interface should keep the port open for its session, not open/close per command.

**Retired, not deleted**: the standalone `usb_bench` sketch/environment. Its full history — the FR-001 reopen, the PCA9555-gate bug, the fix, the real-hardware re-verification — lives in `docs/features/FR-001.md` (marked superseded) and this repo's git history, not silently erased.

## What this is not

- **The four bring-up sketches** (`i2c_scanner`, `pca9555_bringup`, `uart_can_bringup`, `can_address_bringup`) are not application firmware — no relay control logic, no real CAN message parsing/handling, no product behavior. `canopen_app` is different — see its section above — but that's not a claim of hardware verification (next point).
- **Updated 2026-08-10 — real ORC boards exist now, status per sketch**: `i2c_scanner` and `pca9555_bringup` have both run live on a real, powered, fully-wired ORC PCB. `i2c_scanner`: PCA9555 ACKed at 0x20, idle bus HIGH/HIGH, CAN address bank read correctly. `pca9555_bringup`: full 10-channel walking pattern run, user-verified with a DMM in continuity mode against the coil harness — all 10 channels correct, no swaps, no misses. `canopen_app` (USB side): drove all 10 real relays ON, 0.47A real coil current confirmed, matching the ~0.45A design target. `canopen_app` (CAN side) and `uart_can_bringup` have not yet been re-run against the real board/real SN65HVD230/a real CAN bus (a transceiver is being wired up as of this pass) — only the earlier bare-devkit/build-verified history below. Earlier history for context: `i2c_scanner` and `uart_can_bringup` first ran live on a generic ESP32-C3 dev kit before any ORC PCB existed (see "Real-hardware run, 2026-08-01" below) — that confirmed MCU-side IO logic on real silicon of the right chip family, nothing PCA9555/SN65HVD230-related.
- Not a final board declaration — `esp32-c3-devkitm-1` in `platformio.ini` is an explicit stand-in; see above.
- USB is still not the production control path — CAN stays the one real transport in the field, even now that USB control is built into `canopen_app` itself rather than a separate sketch. See `docs/usb-bench-interface-spec.md`'s Scope section for the full "why this doesn't contradict the CAN-exclusive decision" reasoning.
